## English

## [0.4.0rc1] - 2026-10-27

> **Upgrading from 0.3.4?** Most applications need no code changes. Read the **[Migration Guide](docs/MIGRATION_0.4.md)** ([Español](docs/es/MIGRATION_0.4.md)) to check whether any of the three breaking changes below affects you.

### ⚠ BREAKING CHANGES
1. **`GeminiEngine` Uses the Gemini REST API over `httpx`; `google-genai` Removed and Vertex AI No Longer Supported** ([#130](https://github.com/GustavoBaranda/chatflow-agent/pull/130) by [@Gokulnaath07](https://github.com/Gokulnaath07), [#116](https://github.com/GustavoBaranda/chatflow-agent/issues/116)): `GeminiEngine` now calls the Gemini Developer API (Google AI Studio) over REST with an API key, and `google-genai` is no longer a dependency of chatflow-agent (the core runtime dependencies are `pydantic` and `httpx`). Application Default Credentials and the `GOOGLE_GENAI_USE_VERTEXAI`, `GOOGLE_CLOUD_PROJECT` and `GOOGLE_CLOUD_LOCATION` variables, which `google-genai` could use, are ignored; such setups now fail with `ProviderError("Gemini API client is not configured. ...")`. Use a Gemini API key (`GEMINI_API_KEY`, `GOOGLE_API_KEY` or `api_key=...`), or provide your own `BaseEngine` through `Runner(engine=...)`.
2. **`GeminiEngine.client` Removed** ([#130](https://github.com/GustavoBaranda/chatflow-agent/pull/130) by [@Gokulnaath07](https://github.com/Gokulnaath07), [#116](https://github.com/GustavoBaranda/chatflow-agent/issues/116)): the attribute held the `google.genai.Client` (or `None` if it could not be created) and no longer exists. Reading it raises `AttributeError`; assigning it (e.g. a fake client in a test) raises nothing but has no effect, so requests then go to the real API. Migration:
   - **Calling the SDK directly** (e.g. listing models or uploading files): install `google-genai` yourself and create your own `genai.Client`.
   - **Mocking Gemini in tests or customizing HTTP** (proxies, TLS, transports): pass an `httpx.AsyncClient` with `GeminiEngine(http_client=...)`, for example `httpx.AsyncClient(transport=httpx.MockTransport(handler))`, and use the engine through `Runner(engine=...)` (pass the key to `GeminiEngine(api_key=...)` or set `GEMINI_API_KEY`; `Runner(api_key=...)` is then not used). Responses follow the Gemini REST API (`generateContent`), not the SDK's objects. The client belongs to the caller: chatflow-agent never closes it, and it must be used on one event loop only, so it does not suit `Runner.run()` or `CLIChannel`, which start a new event loop per call.
3. **Distinct `Agent` Instances With the Same Name Are Rejected** ([#128](https://github.com/GustavoBaranda/chatflow-agent/pull/128) by [@MbappeWU](https://github.com/MbappeWU), co-authored by [@GustavoBaranda](https://github.com/GustavoBaranda), [#123](https://github.com/GustavoBaranda/chatflow-agent/issues/123)): building a `Runner` whose handoff graph contains two distinct `Agent` instances with the same `name` now raises `ValueError`; previously the second instance was silently ignored and its handoffs went to the first one. The same check applies to `add_handoff()` after initialization and to `register_agent()`; a rejected change leaves the registry untouched. Reusing one `Agent` instance on several branches, or in cycles, keeps working. Give each distinct agent a unique name.

### Added
- **Connection Pooling with `async with runner:`** ([#130](https://github.com/GustavoBaranda/chatflow-agent/pull/130) by [@Gokulnaath07](https://github.com/Gokulnaath07)): inside an `async with runner:` scope, the Gemini requests the runner makes on that event loop share one pooled `httpx` client, closed when the scope exits; outside it each request attempt uses its own client, as before. `Runner.run()`, `TelegramChannel.run()` and the `WhatsAppChannel` app open this scope automatically. `GeminiEngine` also accepts `http_client=...` and `api_key_in_query=True`, and honours `GOOGLE_GEMINI_BASE_URL`.
- **`Runner.run_async(..., turn_timeout=...)`** ([#131](https://github.com/GustavoBaranda/chatflow-agent/pull/131) by [@GustavoBaranda](https://github.com/GustavoBaranda)): optional keyword-only limit, in seconds, for the turn itself. It starts once the turn holds the session lock, so waiting behind earlier turns does not count. On expiry the turn is cancelled, the session is restored to its state before the turn, and `TimeoutError` (`asyncio.TimeoutError`) is raised. It must be a positive finite number; the default, `None`, keeps the previous behaviour.
- **`WhatsAppChannel(queue_timeout_seconds=120.0)`** ([#131](https://github.com/GustavoBaranda/chatflow-agent/pull/131) by [@GustavoBaranda](https://github.com/GustavoBaranda)): limit for the wait behind earlier turns of the same session. Must be a positive finite number.
- **`Runner.spawn_turn()`** ([#120](https://github.com/GustavoBaranda/chatflow-agent/pull/120) by [@GustavoBaranda](https://github.com/GustavoBaranda), [#31](https://github.com/GustavoBaranda/chatflow-agent/issues/31)): starts a turn as an independent task, outside any running turn. Tools use it to queue a follow-up turn for their own session; it runs after the current turn ends and must not be awaited inside it. The runner keeps the task alive until it finishes.
- **In-Memory SQLite Stores and Store Lifecycle** ([#107](https://github.com/GustavoBaranda/chatflow-agent/pull/107) by [@dbdefault](https://github.com/dbdefault), [#103](https://github.com/GustavoBaranda/chatflow-agent/issues/103); [#133](https://github.com/GustavoBaranda/chatflow-agent/pull/133) by [@GustavoBaranda](https://github.com/GustavoBaranda)): `SQLiteSessionStore(db_path=":memory:")` keeps its data for the lifetime of the store through one shared, locked connection. `SQLiteSessionStore.close()` and `with SQLiteSessionStore(...) as store:` release the store's resources; for file-backed stores `close()` also shuts down the store's worker threads.
- **`SessionContext.refresh()`** ([#120](https://github.com/GustavoBaranda/chatflow-agent/pull/120) by [@GustavoBaranda](https://github.com/GustavoBaranda), [#31](https://github.com/GustavoBaranda/chatflow-agent/issues/31)): reloads committed state; it is a no-op for in-memory sessions and is called by `Runner` after acquiring the session lock.
- **`Tool.to_openai_parameters()`** ([#118](https://github.com/GustavoBaranda/chatflow-agent/pull/118) by [@rahul05ranjan](https://github.com/rahul05ranjan), [#115](https://github.com/GustavoBaranda/chatflow-agent/issues/115)): returns the normalized JSON Schema `parameters` object used for tool declarations.
- **`/reset` in `CLIChannel`** ([#119](https://github.com/GustavoBaranda/chatflow-agent/pull/119) by [@rahul05ranjan](https://github.com/rahul05ranjan), [#85](https://github.com/GustavoBaranda/chatflow-agent/issues/85)): clears the current session's history without restarting the interactive loop.
- **DeepSeek Model Prefix Detection** ([#55](https://github.com/GustavoBaranda/chatflow-agent/pull/55) by [@HarshRajSinghania](https://github.com/HarshRajSinghania), [#54](https://github.com/GustavoBaranda/chatflow-agent/issues/54)): models starting with `deepseek-` (for example `deepseek-chat`) are routed to the DeepSeek provider by `resolve_engine()` instead of the default Gemini engine.
- **New Public Exceptions:** `ToolSchemaError` ([#118](https://github.com/GustavoBaranda/chatflow-agent/pull/118) by [@rahul05ranjan](https://github.com/rahul05ranjan); exported from `chatflow_agent` in [#136](https://github.com/GustavoBaranda/chatflow-agent/pull/136) by [@GustavoBaranda](https://github.com/GustavoBaranda)), `ReentrantTurnError` (subclass of `ChatFlowError` and `RuntimeError`) and `SessionDeletedError` (subclass of `ChatFlowError`) ([#120](https://github.com/GustavoBaranda/chatflow-agent/pull/120) by [@GustavoBaranda](https://github.com/GustavoBaranda)), all exported from `chatflow_agent`.
- **Documentation:** separate English and Spanish READMEs with contributor recognition ([#137](https://github.com/GustavoBaranda/chatflow-agent/pull/137)), 6-column contributors gallery layout ([#140](https://github.com/GustavoBaranda/chatflow-agent/pull/140)), bilingual architecture guides ([#138](https://github.com/GustavoBaranda/chatflow-agent/pull/138), [#79](https://github.com/GustavoBaranda/chatflow-agent/issues/79)) and the bilingual 0.3.4 → 0.4.0 migration guide ([#139](https://github.com/GustavoBaranda/chatflow-agent/pull/139)), all by [@GustavoBaranda](https://github.com/GustavoBaranda); tool idempotency and side-effect guide ([#71](https://github.com/GustavoBaranda/chatflow-agent/pull/71) by [@SumiRann1](https://github.com/SumiRann1), [#53](https://github.com/GustavoBaranda/chatflow-agent/issues/53)); architecture diagrams ([#76](https://github.com/GustavoBaranda/chatflow-agent/pull/76) by [@GustavoBaranda](https://github.com/GustavoBaranda)); contribution guide, code of conduct, security policy and issue/PR templates ([#22](https://github.com/GustavoBaranda/chatflow-agent/pull/22), [#28](https://github.com/GustavoBaranda/chatflow-agent/pull/28) by [@GustavoBaranda](https://github.com/GustavoBaranda)).

### Changed
- **WhatsApp Timeouts: Queue and Turn Are Limited Separately** ([#93](https://github.com/GustavoBaranda/chatflow-agent/pull/93) by [@dbdefault](https://github.com/dbdefault), [#91](https://github.com/GustavoBaranda/chatflow-agent/issues/91); [#131](https://github.com/GustavoBaranda/chatflow-agent/pull/131) by [@GustavoBaranda](https://github.com/GustavoBaranda)): the default `llm_timeout_seconds` rose from 30 to 120 seconds, and it now bounds only the turn, starting once it holds the session; the wait for the session is bounded by `queue_timeout_seconds`. A reply can therefore take up to `queue_timeout_seconds + llm_timeout_seconds` (240 s with the defaults). A message whose wait expires gets `fallback_message` and its turn never runs. A custom `dispatch_async()` that does not call `Runner.run_async()` is bounded by that sum plus one second. `None` and `inf` still set no turn limit and zero or negative values still time every turn out; `nan` now sets no limit (it used to time turns out at once or, on Python 3.13, stop the event loop). Zero, negative and `nan` values log a warning.
- **WhatsApp Timeout Logs** ([#131](https://github.com/GustavoBaranda/chatflow-agent/pull/131) by [@GustavoBaranda](https://github.com/GustavoBaranda)): the single `LLM dispatch timed out ...` error is replaced by `Session busy ...` (queue limit), `Turn timed out ...` (turn limit), `Dispatch backstop expired ...` (a `dispatch_async()` that never reached `Runner.run_async()`) and `TimeoutError raised while dispatching ...` (a `TimeoutError` raised by the provider or other code). Update alerts that match the old text.
- **Turns Started From Inside a Turn Raise** ([#120](https://github.com/GustavoBaranda/chatflow-agent/pull/120) by [@GustavoBaranda](https://github.com/GustavoBaranda), [#31](https://github.com/GustavoBaranda/chatflow-agent/issues/31)): calling `Runner.run_async()` or `Runner.run()` for a session from code started by a running turn of that same session (a tool, or any task or thread it starts: `create_task`, `gather`, `wait_for`, `TaskGroup`, `asyncio.to_thread`) now raises `ReentrantTurnError` immediately. Previously these calls waited forever (in-memory store) or ran unserialized alongside the outer turn (SQLite). Use `Runner.spawn_turn()` for follow-up turns. This applies to every session store, including custom ones.
- **SQLite Turns Run One at a Time, in Arrival Order** ([#120](https://github.com/GustavoBaranda/chatflow-agent/pull/120), [#133](https://github.com/GustavoBaranda/chatflow-agent/pull/133) by [@GustavoBaranda](https://github.com/GustavoBaranda)): concurrent requests for the same SQLite session are processed sequentially, so a queued request waits for the previous turn. With a file-backed store a turn takes the session lock before loading the session, so turns start in the order they arrive. A turn running when its session is deleted always fails with `SessionDeletedError`.
- **Cancelled Turns Wait for Their Running SQLite Write** ([#133](https://github.com/GustavoBaranda/chatflow-agent/pull/133) by [@GustavoBaranda](https://github.com/GustavoBaranda)): cancelling a turn, or reaching its `turn_timeout`, while one of its SQLite writes is running waits until that write ends, then rolls the turn back, and only then raises; the session stays locked meanwhile. The `TimeoutError` (and the WhatsApp fallback reply) can therefore arrive later: up to SQLite's `busy_timeout` (10 s; somewhat longer on Windows) per pending write while another writer holds the database. A write that has not started yet is withdrawn instead. If the rollback itself fails, its error is raised and logged (`Rolling back the failed turn of session ... failed`); the turn is never reported as rolled back.
- **`GeminiEngine` Retry Delays Are Bounded by `max_delay`** ([#130](https://github.com/GustavoBaranda/chatflow-agent/pull/130) by [@Gokulnaath07](https://github.com/Gokulnaath07), [#116](https://github.com/GustavoBaranda/chatflow-agent/issues/116)): on a 429, 500, 502, 503 or 504 response, a `Retry-After` header (seconds, or an HTTP-date in any of the three formats HTTP allows) replaces the exponential backoff, but the wait never exceeds `max_delay` (10 s by default). A malformed value (for example `soon`, `-5`, `nan` or an invalid date) is ignored and the exponential backoff applies.
- **Unsupported Tool Parameter Types Fail at Registration** ([#118](https://github.com/GustavoBaranda/chatflow-agent/pull/118) by [@rahul05ranjan](https://github.com/rahul05ranjan), [#115](https://github.com/GustavoBaranda/chatflow-agent/issues/115)): a tool parameter whose annotation cannot be expressed as JSON Schema now raises `ToolSchemaError` when the tool is created, instead of being silently declared as a string.
- **Stricter Input Validation:** `Runner.run()` called from a running event loop raises a `RuntimeError` that points to `await runner.run_async(...)` ([#57](https://github.com/GustavoBaranda/chatflow-agent/pull/57) by [@ompatil1906](https://github.com/ompatil1906), [#56](https://github.com/GustavoBaranda/chatflow-agent/issues/56)); empty or whitespace-only `Agent` names raise `ValueError` ([#86](https://github.com/GustavoBaranda/chatflow-agent/pull/86) by [@jay23606](https://github.com/jay23606), [#84](https://github.com/GustavoBaranda/chatflow-agent/issues/84)); non-positive `max_turns` / `default_max_turns` in session contexts and stores raise `ValueError` ([#63](https://github.com/GustavoBaranda/chatflow-agent/pull/63) by [@sarantez](https://github.com/sarantez), [#59](https://github.com/GustavoBaranda/chatflow-agent/issues/59)); `split_message()` with `max_len <= 0` raises `ValueError` instead of looping forever ([#46](https://github.com/GustavoBaranda/chatflow-agent/pull/46) by [@krishna2707](https://github.com/krishna2707), [#45](https://github.com/GustavoBaranda/chatflow-agent/issues/45)).
- **WhatsApp HTTP 413 Status** ([#136](https://github.com/GustavoBaranda/chatflow-agent/pull/136) by [@GustavoBaranda](https://github.com/GustavoBaranda)): `WhatsAppChannel` no longer references Starlette's deprecated `HTTP_413_REQUEST_ENTITY_TOO_LARGE` constant; oversized bodies are still rejected with HTTP 413.
- **Tests, CI and Release Tooling:** mypy is enforced in CI ([#78](https://github.com/GustavoBaranda/chatflow-agent/pull/78)), the GitHub Actions token is restricted to read-only permissions ([#88](https://github.com/GustavoBaranda/chatflow-agent/pull/88)) and publishing verifies tag/version consistency and Git ancestry ([#97](https://github.com/GustavoBaranda/chatflow-agent/pull/97), [#101](https://github.com/GustavoBaranda/chatflow-agent/pull/101)), by [@GustavoBaranda](https://github.com/GustavoBaranda); new or broader tests for the webhook example ([#98](https://github.com/GustavoBaranda/chatflow-agent/pull/98) by [@SumiRann1](https://github.com/SumiRann1), [#83](https://github.com/GustavoBaranda/chatflow-agent/issues/83)), Telegram fallbacks ([#109](https://github.com/GustavoBaranda/chatflow-agent/pull/109) by [@dbdefault](https://github.com/dbdefault), [#106](https://github.com/GustavoBaranda/chatflow-agent/issues/106)), the interactive `CLIChannel.run()` loop ([#135](https://github.com/GustavoBaranda/chatflow-agent/pull/135) by [@madhavidayma21](https://github.com/madhavidayma21)) and queue/turn timeouts ([#132](https://github.com/GustavoBaranda/chatflow-agent/pull/132), [#134](https://github.com/GustavoBaranda/chatflow-agent/pull/134) by [@GustavoBaranda](https://github.com/GustavoBaranda)).

### Fixed
- **Overlapping Synchronous Tools After Turn Timeout** ([#142](https://github.com/GustavoBaranda/chatflow-agent/pull/142) by [@GustavoBaranda](https://github.com/GustavoBaranda)): when a synchronous tool (`def`) running via `asyncio.to_thread()` exceeds `turn_timeout`, its worker thread continues running in the background due to Python thread runtime constraints. The session lock barrier now tracks the running synchronous tool ticket and waits up to `queue_timeout_seconds` before allowing subsequent turns of the same session to acquire the lock. If the worker thread attempts to invoke a nested turn on the same session while draining, it is rejected immediately with `ReentrantTurnError`.
- **SQLite Session Integrity Under Concurrent Requests** ([#120](https://github.com/GustavoBaranda/chatflow-agent/pull/120) by [@GustavoBaranda](https://github.com/GustavoBaranda), [#31](https://github.com/GustavoBaranda/chatflow-agent/issues/31)): turns for the same `session_id` on a `SQLiteSessionStore` now share one lock per event loop; previously every request got its own lock and turns ran in parallel. Each turn reloads the history, active agent and metadata committed by earlier turns after acquiring the lock. A failed or cancelled turn no longer deletes or overwrites what someone else committed meanwhile: it then reverts only its own changes, in a single `BEGIN IMMEDIATE` transaction, and logs a warning. The lock registry holds locks weakly and creates separate locks per event loop, so successive `Runner.run()` calls keep working.
- **SQLite No Longer Blocks the Event Loop** ([#133](https://github.com/GustavoBaranda/chatflow-agent/pull/133) by [@GustavoBaranda](https://github.com/GustavoBaranda)): with a file-backed `SQLiteSessionStore`, the Runner's session calls, the WhatsApp webhook's deduplication write and Telegram's `/reset` run in a small pool of worker threads owned by the store (4 threads, created on first use, shut down by `close()`). A slow disk or a database locked by another writer no longer stops every webhook, session and timeout of the process. `SessionStore`, `:memory:` SQLite stores, subclasses of `SQLiteSessionStore` and custom stores still run on the event loop.
- **Atomic WhatsApp Deduplication on SQLite** ([#120](https://github.com/GustavoBaranda/chatflow-agent/pull/120) by [@GustavoBaranda](https://github.com/GustavoBaranda)): `SQLiteSessionStore.record_processed_message()` checks and records a message id in a single statement, so two concurrent deliveries of the same `wamid` can no longer both be processed. Requires SQLite 3.24 or later.
- **Deleted Sessions No Longer Get Orphan Messages** ([#120](https://github.com/GustavoBaranda/chatflow-agent/pull/120) by [@GustavoBaranda](https://github.com/GustavoBaranda)): a turn that is running when its SQLite session is deleted fails with `SessionDeletedError` instead of storing its reply without a session. A turn waiting for a deleted session starts a new, empty one; deleted content is never restored.
- **Complete Rollback of Failed Turns:** a failed turn restores messages pruned during the turn ([#34](https://github.com/GustavoBaranda/chatflow-agent/pull/34) by [@KeuqS](https://github.com/KeuqS), [#32](https://github.com/GustavoBaranda/chatflow-agent/issues/32)), the active agent and the metadata ([#52](https://github.com/GustavoBaranda/chatflow-agent/pull/52) by [@aazminu](https://github.com/aazminu), [#51](https://github.com/GustavoBaranda/chatflow-agent/issues/51)), also when the turn is cancelled ([#69](https://github.com/GustavoBaranda/chatflow-agent/pull/69) by [@Aaqibhafeezkhan](https://github.com/Aaqibhafeezkhan), [#60](https://github.com/GustavoBaranda/chatflow-agent/issues/60)).
- **Session Metadata Persistence:** `Handoff.context_updates` is stored when a handoff happens ([#41](https://github.com/GustavoBaranda/chatflow-agent/pull/41) by [@mikemikimike](https://github.com/mikemikimike), [#37](https://github.com/GustavoBaranda/chatflow-agent/issues/37)), and metadata passed to `run_async()` is persisted on every turn ([#95](https://github.com/GustavoBaranda/chatflow-agent/pull/95) by [@Erfouni](https://github.com/Erfouni), [#89](https://github.com/GustavoBaranda/chatflow-agent/issues/89)).
- **Handoffs:** handoffs resolve to the peer the current agent declares, so same-named specialists on different branches no longer steal each other's handoffs ([#128](https://github.com/GustavoBaranda/chatflow-agent/pull/128) by [@MbappeWU](https://github.com/MbappeWU), [#123](https://github.com/GustavoBaranda/chatflow-agent/issues/123)); handoffs added with `add_handoff()` after the `Runner` was created are resolved ([#112](https://github.com/GustavoBaranda/chatflow-agent/pull/112) by [@dbdefault](https://github.com/dbdefault), [#105](https://github.com/GustavoBaranda/chatflow-agent/issues/105)); user tools are kept when a handoff tool name collides with them ([#49](https://github.com/GustavoBaranda/chatflow-agent/pull/49) by [@jsdhwfmax](https://github.com/jsdhwfmax), [#48](https://github.com/GustavoBaranda/chatflow-agent/issues/48)); non-ASCII agent names produce distinct handoff tool names ([#108](https://github.com/GustavoBaranda/chatflow-agent/pull/108) by [@dbdefault](https://github.com/dbdefault), [#104](https://github.com/GustavoBaranda/chatflow-agent/issues/104)); reaching `max_handoffs_per_turn` still returns a result for every tool call ([#50](https://github.com/GustavoBaranda/chatflow-agent/pull/50) by [@jsdhwfmax](https://github.com/jsdhwfmax), [#27](https://github.com/GustavoBaranda/chatflow-agent/issues/27)).
- **Tool-Call IDs Across Provider Handoffs** ([#130](https://github.com/GustavoBaranda/chatflow-agent/pull/130) by [@Gokulnaath07](https://github.com/Gokulnaath07), [#116](https://github.com/GustavoBaranda/chatflow-agent/issues/116)): after a handoff between providers, `OpenAIEngine` and `AnthropicEngine` no longer send tool-call IDs the destination rejects. An ID Anthropic does not accept, or one that is empty or longer than 40 characters for `OpenAIEngine(provider="openai")`, is sent as a stable replacement (`call_` and 24 hex digits), the same in the call and in its result; the session history keeps the originals. `GeminiEngine` keeps the `functionCall` IDs Gemini returns and sends them back in the matching `functionResponse`.
- **Engines:** an explicit `Runner(engine=...)` takes precedence over model-prefix detection, while an agent's model prefix wins over the implicit default engine ([#39](https://github.com/GustavoBaranda/chatflow-agent/pull/39) by [@wzd8888](https://github.com/wzd8888), [#38](https://github.com/GustavoBaranda/chatflow-agent/issues/38)); `Role.SYSTEM` messages from the session history are sent to every provider ([#100](https://github.com/GustavoBaranda/chatflow-agent/pull/100) by [@bercedev](https://github.com/bercedev), [#90](https://github.com/GustavoBaranda/chatflow-agent/issues/90)); malformed provider responses raise `ProviderError` with bounded error bodies instead of raw parsing exceptions ([#124](https://github.com/GustavoBaranda/chatflow-agent/pull/124) by [@bfs2021](https://github.com/bfs2021), [#122](https://github.com/GustavoBaranda/chatflow-agent/issues/122)).
- **Tool Schemas:** PEP 604 unions (`X | Y`) are supported ([#26](https://github.com/GustavoBaranda/chatflow-agent/pull/26) by [@KeuqS](https://github.com/KeuqS), [#25](https://github.com/GustavoBaranda/chatflow-agent/issues/25)) and keep their nullability and per-member types ([#118](https://github.com/GustavoBaranda/chatflow-agent/pull/118) by [@rahul05ranjan](https://github.com/rahul05ranjan), [#115](https://github.com/GustavoBaranda/chatflow-agent/issues/115)); `from __future__ import annotations` is resolved ([#72](https://github.com/GustavoBaranda/chatflow-agent/pull/72) by [@SumiRann1](https://github.com/SumiRann1), [#70](https://github.com/GustavoBaranda/chatflow-agent/issues/70)); container annotations ([#40](https://github.com/GustavoBaranda/chatflow-agent/pull/40) by [@kudala-bharani](https://github.com/kudala-bharani), [#36](https://github.com/GustavoBaranda/chatflow-agent/issues/36)) and array `items` schemas ([#87](https://github.com/GustavoBaranda/chatflow-agent/pull/87) by [@SumiRann1](https://github.com/SumiRann1), [#73](https://github.com/GustavoBaranda/chatflow-agent/issues/73)) are generated; `Annotated[T, ...]` keeps the type of `T` ([#62](https://github.com/GustavoBaranda/chatflow-agent/pull/62) by [@sarantez](https://github.com/sarantez)); `functools.partial` objects and callable instances without `__name__` are supported ([#43](https://github.com/GustavoBaranda/chatflow-agent/pull/43) by [@ganeshmshetty](https://github.com/ganeshmshetty), [#42](https://github.com/GustavoBaranda/chatflow-agent/issues/42)), including async ones ([#111](https://github.com/GustavoBaranda/chatflow-agent/pull/111) by [@dbdefault](https://github.com/dbdefault), [#65](https://github.com/GustavoBaranda/chatflow-agent/issues/65)); `*args` and `**kwargs` are excluded ([#35](https://github.com/GustavoBaranda/chatflow-agent/pull/35) by [@mehdimirzafaruk](https://github.com/mehdimirzafaruk), [#30](https://github.com/GustavoBaranda/chatflow-agent/issues/30)); user defaults and properties named `default` survive schema normalization ([#68](https://github.com/GustavoBaranda/chatflow-agent/pull/68) by [@hyverysmart](https://github.com/hyverysmart), [#64](https://github.com/GustavoBaranda/chatflow-agent/issues/64)).
- **WhatsApp Reactions and Malformed Nested Shapes** ([#129](https://github.com/GustavoBaranda/chatflow-agent/pull/129) by [@MbappeWU](https://github.com/MbappeWU), [#121](https://github.com/GustavoBaranda/chatflow-agent/issues/121)): `reaction` and `system` webhook events are acknowledged with no outbound reply. Meta Cloud API payloads that include `entry` never fall through to the generic extractor. Signed payloads whose nested `entry` / `changes` / `value` / `messages` / `text` nodes have an unexpected type are skipped with a warning and HTTP 200, so Meta does not retry them as failures.
- **Webhooks and Examples:** non-object JSON bodies are rejected with HTTP 400 by `WhatsAppChannel` ([#117](https://github.com/GustavoBaranda/chatflow-agent/pull/117) by [@tyza66](https://github.com/tyza66), [#114](https://github.com/GustavoBaranda/chatflow-agent/issues/114)) and by the webhook example ([#110](https://github.com/GustavoBaranda/chatflow-agent/pull/110) by [@Gokulnaath07](https://github.com/Gokulnaath07), [#102](https://github.com/GustavoBaranda/chatflow-agent/issues/102)); generic webhooks without a message id are no longer treated as duplicates ([#94](https://github.com/GustavoBaranda/chatflow-agent/pull/94) by [@Iqranawaz-debug](https://github.com/Iqranawaz-debug), [#92](https://github.com/GustavoBaranda/chatflow-agent/issues/92)); the webhook example reads the correct `AgentResponse` attributes ([#29](https://github.com/GustavoBaranda/chatflow-agent/pull/29) by [@KeuqS](https://github.com/KeuqS), [#24](https://github.com/GustavoBaranda/chatflow-agent/issues/24)) and its tests keep the SQLite database out of the repository root ([#99](https://github.com/GustavoBaranda/chatflow-agent/pull/99) by [@bercedev](https://github.com/bercedev), [#80](https://github.com/GustavoBaranda/chatflow-agent/issues/80)); `examples/multi_provider_swarm.py` uses only public attributes ([#139](https://github.com/GustavoBaranda/chatflow-agent/pull/139) by [@GustavoBaranda](https://github.com/GustavoBaranda)).

### Removed
- `google-genai` dependency and `GeminiEngine.client` attribute ([#130](https://github.com/GustavoBaranda/chatflow-agent/pull/130) by [@Gokulnaath07](https://github.com/Gokulnaath07)); see Breaking Changes 1 and 2.

### Security
- **`GeminiEngine` Credential Handling** ([#130](https://github.com/GustavoBaranda/chatflow-agent/pull/130) by [@Gokulnaath07](https://github.com/Gokulnaath07)): `GeminiEngine` never follows HTTP redirects, even with an injected client configured to (the API key header would be forwarded to another origin), and removes the API key from error messages and logs. This extends to Gemini the redirect policy that 0.3.4 applied to `OpenAIEngine` and `AnthropicEngine`.

### Known Issues
- **Concurrency Scope:** Serialization is not provided across store instances on the same file, across processes, or across threads running their own event loops.
- **Nested Turns Outside the Turn's Tasks:** a tool that waits for work done by a task that was not started from the turn (for example, a worker created earlier) can still deadlock if that work runs a turn of the same session. Awaiting a task returned by `spawn_turn()` inside the turn that spawned it deadlocks as well.
- **SQLite Contention Still Delays the Requests That Need the Database:** an SQLite call that has started cannot be interrupted. While another writer holds the database, the WhatsApp webhook still acknowledges only after its deduplication write (at-most-once semantics are unchanged), so that HTTP response waits; if the lock lasts longer than `busy_timeout`, that webhook fails with HTTP 500 and, since the message was not recorded, Meta's retry is processed. Shutting down can wait for SQLite calls still running. Several workers or processes on one SQLite file are still not supported: running SQLite outside the event loop does not coordinate processes.
- **Reset and Delete During a Turn:** `clear_history()` and `delete()` are not coordinated with running turns beyond the rollback and `SessionDeletedError` guarantees above (tracked separately).

## [0.3.2] - 2026-09-29

### Security
- **Tool Execution Error Sanitization (SEC-02):** Sanitized tool execution errors in `Runner` before exposing them to the LLM, returning a generic error with a unique `trace_id` UUID and logging the original traceback internally to prevent leakage of internal stack traces or environment variables (Issue #3).

Interactive documentation can be optionally enabled for development via `enable_docs=True` (Issue #9).
- **Reverse Proxy Rate Limiting Recommendation (SEC-06):** Added production deployment guidance for placing Uvicorn behind a reverse proxy (e.g., Nginx with `limit_req_zone` or Cloudflare Rate Limiting) to protect `/webhook` and `/health` endpoints against flood attacks and CPU exhaustion from unauthenticated requests, avoiding in-app rate limiting that could drop legitimate bursts of Meta webhooks (Issue #10).

## [0.3.1] - 2026-09-25

### Security
- **WhatsApp Webhook Request Body Size Limit (SEC-01):** Fixed vulnerability where inbound `POST /webhook` requests did not validate the payload size prior to buffering, enabling potential Denial of Service (DoS via Out-of-Memory / OOM). ## [0.3.0] - 2026-09-21

### Security
- **WhatsApp Webhook Signature Verification Enforced (SEC-01):** Fixed vulnerability where inbound POST `/webhook` requests were processed without verifying Meta's `X-Hub-Signature-256` HMAC header, allowing unauthenticated attackers to forge messages. `WhatsAppChannel` now enforces a strict fail-closed policy: `app_secret` is required by default, validating requests with constant-time `hmac.compare_digest` and rejecting invalid or missing signatures with HTTP 403.
- **Timing Attack Mitigation (SEC-02):** GET `/webhook` challenge verification now uses constant-time `hmac.compare_digest` for verify tokens.
- **Credential Masking in Logs:** Sensitive tokens, app secrets, and credentials are automatically redacted across all logging handlers.
- **Fail-Closed Starter Templates:** Example scripts (`whatsapp_service.py`, `whatsapp_persistent_bot.py`) raise `RuntimeError` if `WHATSAPP_APP_SECRET` is unset rather than falling back to an insecure development secret.

### ⚠ BREAKING CHANGES
1. **`WhatsAppChannel` requires `app_secret` by default (SEC-01):** Omitting `app_secret` raises `ValueError` on startup unless `verify_signature=False` is explicitly set (local testing only).
2. **Webhook response payload changed (BUS-01):** POST `/webhook` returns `{"status":"success","sender":"...","messages_queued": N}`. Inference and messaging are now dispatched asynchronously in background tasks.
3. **`max_turns` counts complete user conversation turns (DATA-01):** `max_turns` now enforces complete user dialogue turns (user message + model responses + tool results) rather than individual message objects.

### Added / Fixed
- **Background Webhook Dispatch (BUS-01):** Webhooks respond HTTP 200 to Meta immediately, preventing timeout retries on slow LLM calls.
- **At-Most-Once Deduplication (ARCH-01):** Atomic message ID tracking in SQLite with an 8-day TTL (`DEFAULT_DEDUP_TTL_HOURS = 192`) safely discards Meta retries.
- **Multi-Message Batch Extraction:** Webhooks with multiple message payloads are unpacked and dispatched independently.
- **Selective Outbound Retry Backoff with Jitter:** Outbound HTTP retries are strictly limited to `ConnectError`, `ConnectTimeout`, and HTTP 429, honoring the `Retry-After` header.
- **Meta 24h Window Expiration Handling:** Detects Meta error code `131047`, executes optional `on_24h_window_expired` callback safely (try/except), and logs masked recipient numbers.
- **Outbound Message Splitting:** Messages exceeding Meta's 4,096-character limit are automatically split across paragraph and sentence boundaries into sequential chunks.
- **Mid-Turn Failure Rollback:** Automatically reverts dialogue history to the last consistent turn in memory and SQLite on mid-turn engine failure and guarantees fallback delivery to WhatsApp.
- **Turn-Based Pruning & Memory Integrity (DATA-01):** FIFO pruning preserves system prompts and atomic tool call/result pairs.
- **SQLite Concurrency & WAL Mode:** Configured `PRAGMA busy_timeout = 10000` and `PRAGMA journal_mode = WAL` for atomic multi-reader concurrency. Existing databases transition automatically without schema recreation.
- **Documentation Parity:** 100% bilingual parity across README and CHANGELOG.

### Migration Guide
If you are upgrading from v0.2.0:
1. **Set `WHATSAPP_APP_SECRET`:** Add your Meta App Secret to your environment variables and pass it to `WhatsAppChannel(..., app_secret=os.environ["WHATSAPP_APP_SECRET"])`. For local testing without signature validation, explicitly pass `verify_signature=False`.
2. **Update Webhook Payload Parsing:** If any internal client monitored the POST `/webhook` response body, update it to expect `{"status": "success", "messages_queued": N}` instead of the synchronous `reply` field.
3. **Reduce `max_turns` Setting:** If your configuration previously used inflated `max_turns` values to account for individual messages (e.g. `max_turns=40` which held ~10 real turns), reduce it to the number of full turns you actually want to retain (e.g., lower to `max_turns=10`). Keeping the old number will retain roughly 4x more context than before.

Leerlo levanta `AttributeError`; asignarlo (por ejemplo, un cliente simulado en un test) no genera excepción pero no tiene ningún efecto, enviando las peticiones a la API real. Migración:
   - **Llamadas directas al SDK** (por ejemplo, listar modelos o subir archivos): instalá `google-genai` por tu cuenta y creá tu propio `genai.Client`.
   - **Mocking de Gemini en tests o personalización de HTTP** (proxies, TLS, transportes): pasá un `httpx.AsyncClient` con `GeminiEngine(http_client=...)`, por ejemplo `httpx.AsyncClient(transport=httpx.MockTransport(handler))`, y utilizá el motor a través de `Runner(engine=...)` (proporcioná la clave a `GeminiEngine(api_key=...)` o definí `GEMINI_API_KEY`; en tal caso `Runner(api_key=...)` no se utiliza). Las respuestas siguen la API REST de Gemini (`generateContent`), no los objetos del SDK. El cliente pertenece a quien lo invoca: chatflow-agent nunca lo cierra y debe utilizarse en un único bucle de eventos, por lo que no es apto para `Runner.run()` ni `CLIChannel`, que inician un bucle nuevo en cada llamada.
3. **Se Rechazan Instancias Distintas de `Agent` con el Mismo Nombre** ([#128](https://github.com/GustavoBaranda/chatflow-agent/pull/128) por [@MbappeWU](https://github.com/MbappeWU), coautoría con [@GustavoBaranda](https://github.com/GustavoBaranda), [#123](https://github.com/GustavoBaranda/chatflow-agent/issues/123)): construir un `Runner` cuyo grafo de handoffs contenga dos instancias distintas de `Agent` con el mismo `name` ahora levanta `ValueError`; anteriormente la segunda instancia se ignoraba silenciosamente y sus handoffs se redirigían a la primera. La misma verificación aplica a `add_handoff()` tras la inicialización y a `register_agent()`; un cambio rechazado deja el registro sin alterar. Reutilizar una misma instancia de `Agent` en varias ramas o en ciclos sigue funcionando normalmente. Asigná a cada agente distinto un nombre único.

### Agregado
- **Pool de Conexiones con `async with runner:`** ([#130](https://github.com/GustavoBaranda/chatflow-agent/pull/130) por [@Gokulnaath07](https://github.com/Gokulnaath07)): dentro del contexto `async with runner:`, las peticiones a Gemini realizadas por el runner en ese bucle de eventos comparten un único cliente `httpx` en pool, cerrado al salir del bloque; fuera de este ámbito, cada intento de petición utiliza su propio cliente, como antes. `Runner.run()`, `TelegramChannel.run()` y la aplicación de `WhatsAppChannel` abren este contexto automáticamente. `GeminiEngine` también acepta `http_client=...` y `api_key_in_query=True`, y respeta `GOOGLE_GEMINI_BASE_URL`.
- **`Runner.run_async(..., turn_timeout=...)`** ([#131](https://github.com/GustavoBaranda/chatflow-agent/pull/131) por [@GustavoBaranda](https://github.com/GustavoBaranda)): límite opcional, solo por nombre y en segundos, para el turno en sí. - **`Runner.spawn_turn()`** ([#120](https://github.com/GustavoBaranda/chatflow-agent/pull/120) por [@GustavoBaranda](https://github.com/GustavoBaranda), [#31](https://github.com/GustavoBaranda/chatflow-agent/issues/31)): inicia un turno como tarea independiente, fuera de cualquier turno en curso. ### Modificado
- **Timeouts de WhatsApp: Espera y Turno se Limitan por Separado** ([#93](https://github.com/GustavoBaranda/chatflow-agent/pull/93) por [@dbdefault](https://github.com/dbdefault), [#91](https://github.com/GustavoBaranda/chatflow-agent/issues/91); [#131](https://github.com/GustavoBaranda/chatflow-agent/pull/131) por [@GustavoBaranda](https://github.com/GustavoBaranda)): el valor por defecto de `llm_timeout_seconds` aumentó de 30 a 120 segundos, y ahora acota únicamente la duración del turno desde que adquiere la sesión; la espera por la sesión está acotada por `queue_timeout_seconds`. Una respuesta puede tardar hasta `queue_timeout_seconds + llm_timeout_seconds` (240 s con los valores por defecto). Un mensaje cuya espera vence recibe `fallback_message` y su turno nunca se ejecuta. Un método `dispatch_async()` personalizado que no invoque `Runner.run_async()` queda acotado por dicha suma más un segundo. `None` e `inf` siguen sin aplicar límite de turno, y valores menores o iguales a cero hacen vencer cada turno de inmediato; `nan` ahora no impone límite (anteriormente causaba vencimientos inmediatos o detenía el bucle en Python 3.13). Valores menores o iguales a cero o `nan` emiten una advertencia en el log.
- **Logs de Timeout en WhatsApp** ([#131](https://github.com/GustavoBaranda/chatflow-agent/pull/131) por [@GustavoBaranda](https://github.com/GustavoBaranda)): el mensaje único de error `LLM dispatch timed out ...` se reemplaza por `Session busy ...` (límite de cola), `Turn timed out ...` (límite de turno), `Dispatch backstop expired ...` (un `dispatch_async()` que nunca invocó `Runner.run_async()`) y `TimeoutError raised while dispatching ...` (un `TimeoutError` emitido por el proveedor u otro componente). Es necesario actualizar alertas que filtren por el texto previo.
- **Llamadas a Turnos desde un Turno Activo Levantan Excepción** ([#120](https://github.com/GustavoBaranda/chatflow-agent/pull/120) por [@GustavoBaranda](https://github.com/GustavoBaranda), [#31](https://github.com/GustavoBaranda/chatflow-agent/issues/31)): invocar `Runner.run_async()` o `Runner.run()` para una sesión desde código ejecutado por un turno en curso de esa misma sesión (una herramienta, o cualquier tarea o hilo que inicie: `create_task`, `gather`, `wait_for`, `TaskGroup`, `asyncio.to_thread`) ahora levanta `ReentrantTurnError` inmediatamente. Con anterioridad, dichas llamadas se bloqueaban indefinidamente (almacenamiento en memoria) o se ejecutaban concurrentemente sin serializar junto al turno externo (SQLite). Utilizá `Runner.spawn_turn()` para turnos de seguimiento. Aplica a cualquier implementación de almacenamiento de sesión, incluyendo stores personalizados.
- **Turnos en SQLite se Procesan Secuencialmente por Orden de Llegada** ([#120](https://github.com/GustavoBaranda/chatflow-agent/pull/120), [#133](https://github.com/GustavoBaranda/chatflow-agent/pull/133) por [@GustavoBaranda](https://github.com/GustavoBaranda)): peticiones concurrentes sobre un mismo `session_id` en SQLite se ejecutan de manera estrictamente secuencial, esperando la solicitud encolada al turno previo. En stores respaldados por archivo, el turno adquiere el candado antes de cargar el estado, garantizando el orden de inicio. Un turno que se encuentra ejecutándose al momento de eliminarse su sesión falla indefectiblemente con `SessionDeletedError`.
- **Turnos Cancelados Aguardan la Finalización de su Escritura SQLite en Curso** ([#133](https://github.com/GustavoBaranda/chatflow-agent/pull/133) por [@GustavoBaranda](https://github.com/GustavoBaranda)): cancelar un turno o alcanzar su `turn_timeout` mientras una escritura SQLite está en ejecución espera a que dicha operación concluya, luego ejecuta el rollback del turno y recién entonces propaga la excepción; la sesión permanece bloqueada durante dicho intervalo. La detección del timeout ocurre puntualmente, pero su `TimeoutError` (y la respuesta de fallback en WhatsApp) pueden emitirse posteriormente: hasta el lapso de `busy_timeout` de SQLite (10 s; algo mayor en Windows) por escritura pendiente mientras otro proceso retiene la base. Una escritura que no haya iniciado aún es cancelada de inmediato. Si el propio rollback falla, se levanta y registra su error (`Rolling back the failed turn of session ... failed`); el turno nunca se reporta como revertido exitosamente.
- **Tiempos de Reintento en `GeminiEngine` Acotados por `max_delay`** ([#130](https://github.com/GustavoBaranda/chatflow-agent/pull/130) por [@Gokulnaath07](https://github.com/Gokulnaath07), [#116](https://github.com/GustavoBaranda/chatflow-agent/issues/116)): ante respuestas 429, 500, 502, 503 o 504, el encabezado `Retry-After` (segundos o fecha HTTP en cualquiera de los tres formatos estándar) reemplaza al backoff exponencial, pero la espera nunca excede `max_delay` (10 s por defecto). Valores malformados (por ejemplo `soon`, `-5`, `nan` o fechas inválidas) se ignoran, aplicándose el backoff exponencial habitual.
- **Tipos de Parámetro No Soportados en Herramientas Fallan al Registrarse** ([#118](https://github.com/GustavoBaranda/chatflow-agent/pull/118) por [@rahul05ranjan](https://github.com/rahul05ranjan), [#115](https://github.com/GustavoBaranda/chatflow-agent/issues/115)): un parámetro de herramienta cuya anotación no pueda traducirse a JSON Schema levanta `ToolSchemaError` al momento de inicializar la herramienta, en vez de registrarse silenciosamente como tipo `string`.

### Corregido
- **Herramientas Síncronas Solapadas tras Timeout de Turno** ([#142](https://github.com/GustavoBaranda/chatflow-agent/pull/142) por [@GustavoBaranda](https://github.com/GustavoBaranda)): cuando una herramienta síncrona (`def`) ejecutada mediante `asyncio.to_thread()` excede `turn_timeout`, su hilo de trabajo continúa ejecutándose en segundo plano debido a restricciones del runtime de hilos en Python. La barrera del candado de sesión ahora registra el ticket del trabajo síncrono activo y aguarda hasta `queue_timeout_seconds` antes de permitir que turnos subsiguientes en la misma sesión adquieran el candado. Si el hilo de trabajo intenta invocar un turno anidado en la misma sesión mientras drena, es rechazado inmediatamente con `ReentrantTurnError`.
- **Integridad de Sesiones SQLite ante Solicitudes Concurrentes** ([#120](https://github.com/GustavoBaranda/chatflow-agent/pull/120) por [@GustavoBaranda](https://github.com/GustavoBaranda), [#31](https://github.com/GustavoBaranda/chatflow-agent/issues/31)): turnos sobre un mismo `session_id` en `SQLiteSessionStore` comparten un candado por bucle de eventos; anteriormente cada solicitud obtenía un candado independiente y corrían en paralelo. Cada turno recarga el historial, agente activo y metadata confirmados tras obtener el candado. Un turno fallido o cancelado no elimina ni sobrescribe datos confirmados concurrentemente: revierte únicamente sus propias modificaciones mediante una única transacción `BEGIN IMMEDIATE` y emite una advertencia. El registro de candados utiliza referencias débiles (`WeakValueDictionary`) y segrega candados por bucle de eventos, manteniendo la compatibilidad con llamadas sucesivas a `Runner.run()`.
- **SQLite No Bloquea el Bucle de Eventos** ([#133](https://github.com/GustavoBaranda/chatflow-agent/pull/133) por [@GustavoBaranda](https://github.com/GustavoBaranda)): en almacenes `SQLiteSessionStore` basados en archivo, las operaciones de sesión del Runner, la deduplicación del webhook de WhatsApp y `/reset` en Telegram se delegan a un pool dedicado de hilos de trabajo propio del almacén (4 hilos, inicializados en el primer uso y cerrados vía `close()`). Latencias de disco o bloqueos por otros procesos ya no suspenden el bucle de eventos de la aplicación. Almacenes en memoria (`:memory:`), clases base `SessionStore`, subclases e implementaciones personalizadas continúan operando en el bucle principal.
- **Deduplicación Atómica de WhatsApp en SQLite** ([#120](https://github.com/GustavoBaranda/chatflow-agent/pull/120) por [@GustavoBaranda](https://github.com/GustavoBaranda)): `SQLiteSessionStore.record_processed_message()` verifica y almacena el identificador del mensaje en una única sentencia, impidiendo el procesamiento dual ante entregas concurrentes del mismo `wamid`. Requiere SQLite 3.24 o posterior.
- **Sesiones Eliminadas No Reciben Mensajes Huérfanos** ([#120](https://github.com/GustavoBaranda/chatflow-agent/pull/120) por [@GustavoBaranda](https://github.com/GustavoBaranda)): un turno en ejecución cuya sesión SQLite es borrada falla con `SessionDeletedError` en lugar de guardar respuestas desvinculadas. Un turno en espera de una sesión eliminada inicia una sesión nueva y vacía; los datos eliminados nunca se restauran.
- **Rollback Completo de Turnos Fallidos:** un turno fallido restaura mensajes podados durante el turno ([#34](https://github.com/GustavoBaranda/chatflow-agent/pull/34) por [@KeuqS](https://github.com/KeuqS), [#32](https://github.com/GustavoBaranda/chatflow-agent/issues/32)), el agente activo y la metadata ([#52](https://github.com/GustavoBaranda/chatflow-agent/pull/52) por [@aazminu](https://github.com/aazminu), [#51](https://github.com/GustavoBaranda/chatflow-agent/issues/51)), aplicándose igualmente ante cancelaciones ([#69](https://github.com/GustavoBaranda/chatflow-agent/pull/69) por [@Aaqibhafeezkhan](https://github.com/Aaqibhafeezkhan), [#60](https://github.com/GustavoBaranda/chatflow-agent/issues/60)).

- **Webhooks y Ejemplos:** cuerpos JSON que no constituyen objetos son rechazados con HTTP 400 por `WhatsAppChannel` ([#117](https://github.com/GustavoBaranda/chatflow-agent/pull/117) por [@tyza66](https://github.com/tyza66), [#114](https://github.com/GustavoBaranda/chatflow-agent/issues/114)) y por el servicio de ejemplo ([#110](https://github.com/GustavoBaranda/chatflow-agent/pull/110) por [@Gokulnaath07](https://github.com/Gokulnaath07), [#102](https://github.com/GustavoBaranda/chatflow-agent/issues/102)); webhooks genéricos sin ID de mensaje no son clasificados falsamente como duplicados ([#94](https://github.com/GustavoBaranda/chatflow-agent/pull/94) por [@Iqranawaz-debug](https://github.com/Iqranawaz-debug), [#92](https://github.com/GustavoBaranda/chatflow-agent/issues/92)); el ejemplo de webhook lee los atributos correctos de `AgentResponse` ([#29](https://github.com/GustavoBaranda/chatflow-agent/pull/29) por [@KeuqS](https://github.com/KeuqS), [#24](https://github.com/GustavoBaranda/chatflow-agent/issues/24)) y sus tests mantienen la base SQLite fuera del directorio raíz ([#99](https://github.com/GustavoBaranda/chatflow-agent/pull/99) por [@bercedev](https://github.com/bercedev), [#80](https://github.com/GustavoBaranda/chatflow-agent/issues/80)); `examples/multi_provider_swarm.py` utiliza exclusivamente atributos públicos ([#139](https://github.com/GustavoBaranda/chatflow-agent/pull/139) por [@GustavoBaranda](https://github.com/GustavoBaranda)).

### Seguridad
- **Manejo de Credenciales en `GeminiEngine`** ([#130](https://github.com/GustavoBaranda/chatflow-agent/pull/130) por [@Gokulnaath07](https://github.com/Gokulnaath07)): `GeminiEngine` nunca sigue redirecciones HTTP, incluso si el cliente inyectado está configurado para hacerlo (evitando reenviar el encabezado de clave API a otro origen), y remueve la clave API de los mensajes de error y registros de log. Esto extiende a Gemini la política de redirecciones aplicada en la versión 0.3.4 a `OpenAIEngine` y `AnthropicEngine`.

### Problemas Conocidos
- **Alcance de la Concurrencia:** No se provee serialización entre instancias de almacenamiento sobre el mismo archivo, entre procesos independientes ni entre hilos con bucles de eventos desacoplados.
- **Turnos Anidados Externos a las Tareas del Turno:** una herramienta que aguarde la finalización de trabajo delegado en una tarea externa (por ejemplo, un worker previo) puede bloquearse si dicho trabajo invoca un turno para la misma sesión. Esperar con `await` una tarea devuelta por `spawn_turn()` dentro del mismo turno que la creó genera igualmente interbloqueo.
- **Contención en SQLite Retrasa Peticiones que Requieren la Base:** una operación SQLite iniciada no puede interrumpirse. Mientras otro proceso retiene la base, el webhook de WhatsApp confirmará únicamente tras su escritura de deduplicación (preservando la semántica at-most-once), esperando dicha respuesta HTTP; si la contención supera `busy_timeout`, el webhook responderá HTTP 500 y el reintento de Meta será procesado al no haberse registrado el mensaje. El apagado del servicio puede aguardar escrituras en curso. No se soporta la concurrencia de múltiples procesos sobre un mismo archivo SQLite: ejecutar SQLite fuera del bucle de eventos no coordina procesos externos.
- **Reset y Delete Durante un Turno:** `clear_history()` y `delete()` no coordinan transacciones con turnos en curso más allá de las garantías de rollback y excepciones `SessionDeletedError` documentadas previamente (seguimiento por separado).

### Seguridad

## [0.3.0] - 2026-09-21

### Seguridad
- **Verificación Obligatoria de Firma en Webhook de WhatsApp (SEC-01):** Se corrigió una vulnerabilidad en `WhatsAppChannel` donde las peticiones POST `/webhook` entrantes se procesaban sin validar la cabecera HMAC `X-Hub-Signature-256` de Meta, permitiendo a un atacante enviar mensajes falsificados suplantando números de usuario. `WhatsAppChannel` ahora aplica una política estricta *fail-closed*: exige `app_secret` por defecto, valida la firma con `hmac.compare_digest` en tiempo constante y rechaza cualquier petición sin firma válida con HTTP 403.
- **Mitigación de Ataques de Temporización (SEC-02):** La verificación del handshake GET `/webhook` utiliza `hmac.compare_digest` en tiempo constante para validar el token.
- **Enmascaramiento de Credenciales en Logs:** Tokens, secretos de aplicación y números telefónicos se enmascaran automáticamente en toda la salida de depuración y logs.
- **Plantillas con Validación Estricta (Fail-Closed):** Los ejemplos (`whatsapp_service.py` y `whatsapp_persistent_bot.py`) lanzan `RuntimeError` si falta `WHATSAPP_APP_SECRET` en vez de usar un secreto de desarrollo inseguro por defecto.

### ⚠ CAMBIOS CON RUPTURA DE COMPATIBILIDAD (BREAKING CHANGES)
1. **`WhatsAppChannel` exige `app_secret` por defecto (SEC-01):** Si se omite `app_secret`, se lanza `ValueError` al arrancar el servidor a menos que se configure explícitamente `verify_signature=False` (solo para pruebas locales).
2. **Cambio en el cuerpo de respuesta del Webhook (BUS-01):** El POST `/webhook` ahora responde `{"status":"success","sender":"...","messages_queued": N}`. La inferencia y el envío saliente se procesan asíncronamente en segundo plano.
3. **`max_turns` ahora cuenta turnos completos de usuario (DATA-01):** `max_turns` mide ciclos conversacionales completos (mensaje del usuario + respuestas del modelo + herramientas asociadas) en vez de objetos de mensaje individuales.

### Agregado / Corregido
- **Despacho Asíncrono de Webhooks (BUS-01):** Responde HTTP 200 a Meta inmediatamente, evitando tormentas de reintentos por latencia del LLM.
- **Deduplicación At-Most-Once (ARCH-01):** Registro atómico por `wamid` en SQLite con TTL de 8 días (`DEFAULT_DEDUP_TTL_HOURS = 192`) que descarta reintentos duplicados de Meta.
- **Extracción de Lotes Multi-Mensaje:** Procesamiento y despacho independiente para webhooks que contienen múltiples mensajes simultáneos.
- **Reintentos Salientes Selectivos con Jitter:** Limitados estrictamente a errores de conexión de red y HTTP 429 con jitter, respetando el encabezado `Retry-After`.
- **Manejo de Ventana de 24h de Meta:** Detección del código de error `131047`, ejecución protegida con try/except del hook `on_24h_window_expired` y log con teléfono enmascarado.
- **División Automática de Mensajes Salientes:** Fragmentación automática de mensajes que exceden el límite de 4.096 caracteres de Meta respetando párrafos y oraciones.
- **Rollback ante Fallas a Mitad de Turno:** Reversión automática del historial conversacional al último turno consistente en memoria y SQLite ante fallas del LLM, garantizando la entrega del mensaje de fallback.
- **Integridad de Memoria y Poda por Turnos (DATA-01):** Poda FIFO que preserva el prompt del sistema y mantiene indivisibles los pares de llamadas y resultados de herramientas.
- **Concurrencia SQLite y Modo WAL:** `PRAGMA busy_timeout = 10000` y `PRAGMA journal_mode = WAL` para concurrencia multi-lector sin contención. Bases existentes transicionan automáticamente sin recreación de tablas.
- **Paridad Bilingüe en Documentación:** Paridad 100% en inglés y español en README y CHANGELOG.

### Guía de Migración
Si ya instalaste o integraste la versión v0.2.0:
1. **Configurá `WHATSAPP_APP_SECRET`:** Agregá tu App Secret de Meta a las variables de entorno y pasalo a `WhatsAppChannel(..., app_secret=os.environ["WHATSAPP_APP_SECRET"])`. Si estás testeando localmente sin firma, pasá explícitamente `verify_signature=False`.
2. **Actualizá el parseo de respuesta del Webhook:** Si tenías clientes o scripts esperando el campo sincrónico `reply` en el JSON de respuesta de POST `/webhook`, actualizalos para esperar `{"status": "success", "messages_queued": N}`.
3. **Reducí el valor de `max_turns`:** Si tu configuración anterior inflaba `max_turns` para contar mensajes sueltos (por ejemplo, `max_turns=40` para retener unos ~10 turnos reales), reducilo al número real de turnos deseados (por ejemplo, bajalo a `max_turns=10`). Mantener el número anterior retendrá aproximadamente 4 veces más contexto que antes.
