## [Unreleased]

### Fixed
- **Accurate `engine` Type Annotation on `Agent`** ([#220](https://github.com/GustavoBaranda/chatflow-agent/issues/220)): `Agent.__init__` and `Agent.engine` are now annotated as `BaseEngine | None` instead of `Any | None`, so static type checkers (`mypy`, `pyright`) catch invalid engines without changing runtime behavior. CI verifies this in `tests/type_checks/agent_engine.py` with `mypy --strict tests/type_checks`.
  - **Virtual `BaseEngine` subclasses:** an engine registered with `BaseEngine.register()` without inheriting from `BaseEngine` still passes the runtime `isinstance` check and works with `Agent(engine=...)` and `Runner(engine=...)`, but static type checkers such as Mypy reject it as an argument (`arg-type`), because they do not recognize virtual subclasses. Inherit explicitly from `BaseEngine`, or pass `cast(BaseEngine, engine)`.
- **CLI `/reset` Uses `Runner.reset_session()`** ([#242](https://github.com/GustavoBaranda/chatflow-agent/pull/242) by [@helmipradita](https://github.com/helmipradita), [#240](https://github.com/GustavoBaranda/chatflow-agent/issues/240)): `CLIChannel` now clears the session history through `Runner.reset_session()` instead of calling `clear_history()` on the session directly, so the reset waits for any active turn and residual synchronous tool work on that session and runs while holding the session lock. The session metadata and active agent are kept, the printed message is unchanged, and `/reset` for a session that does not exist creates nothing.

## [0.4.0] - 2026-11-22

First stable release of the `0.4.x` series, consolidating all changes from `0.4.0rc1`, `0.4.0rc2`, and `0.4.0rc3` together with post-`rc3` synthetic tool-call ID fixes for `OpenAIEngine` and `GeminiEngine`. See the individual release-candidate sections below for full per-PR detail and contributor attributions.

### Highlights & New Features
- **Turn Timeouts, Deferred Turns & Safe Session Resets:** Added `Runner.run_async(..., turn_timeout=...)`, `Runner.spawn_turn()` for deferred follow-up turns outside the active turn lock, `Runner.reset_session_async()` / `Runner.reset_session()`, `SessionContext.refresh()`, and `/reset` in `CLIChannel`.
- **In-Memory SQLite & Store Lifecycle:** Added `SQLiteSessionStore(db_path=":memory:")`, explicit `close()`, and `with SQLiteSessionStore(...) as store:` context-manager cleanup.
- **New Public Exceptions & Documentation:** Exported `ToolSchemaError`, `ToolArgumentValidationError`, `ConfigurationError`, `JsonCodecError`, `ReentrantTurnError`, and `SessionDeletedError` from `chatflow_agent`; added bilingual Architecture, `0.3.4` → `0.4.0` Migration, and Troubleshooting guides.

### Engines & Providers
- **Native `httpx` `GeminiEngine`:** Replaced the `google-genai` SDK with direct Gemini Developer REST API (`v1beta`) requests over `httpx`, supporting `http_client=...`, `api_key_in_query=True`, `GOOGLE_GEMINI_BASE_URL`, and `Retry-After` delays bounded by `max_delay`.
- **Configurable `AnthropicEngine` & Provider Routing:** Added `AnthropicEngine(..., max_tokens=4096)` with truncation warning logs (`stop_reason == "max_tokens"`), `deepseek-` model prefix detection, strict `ConfigurationError` validation for unknown providers or invalid endpoint combinations (no silent fallbacks), and `Agent(api_key=...)` propagation on default Gemini fallback.
- **Cross-Provider Tool-Call ID Normalization:** Added collision-resistant stateless synthetic fallback IDs for `OpenAIEngine` (`#213`/`#230`) and `GeminiEngine` (`#231`/`#232`).

### Tools & Validation
- **Runtime Pydantic Argument Validation:** Enabled `validate_args=True` by default (`ToolArgumentValidationError`, opt-out with `validate_args=False`), order-independent union validation (`str | int`), and strict finite numeric checks (`allow_inf_nan=False`).
- **Schema & Typing Improvements:** Unrepresentable union members raise `ToolSchemaError` at registration, `@tool` / `@agent.tool` provide precise `@overload` static types, plain functions with `self`/`cls` parameters remain intact in schemas, `Tool.to_openai_parameters()` exposes normalized JSON Schemas, and unified `json_codec` serialization raises `JsonCodecError` on non-JSON session metadata.

### Sessions, SQLite & Concurrency
- **Serialized, Non-Blocking SQLite Execution:** Per-session arrival-order serialization, worker-thread offloading for file-backed SQLite stores, cancellation/timeout rollbacks that wait for in-flight SQLite writes before restoring state, `ReentrantTurnError` lineage protection, and `SessionDeletedError` deletion guards.
- **In-Memory Isolation & Thread Safety:** Thread-safe `SessionStore` deduplication (`record_processed_message()` / `is_message_processed()`) and deep-copied in-memory session metadata isolation.

### Telegram & WhatsApp Integrations
- **`TelegramChannel`:** Added `concurrent_updates` support, session-safe `/reset` coordinated through `Runner.reset_session_async()`, and bounded `RetryAfter` flood-control retries (`max_retry_after_seconds=60.0`) without duplicating sent chunks or sending contradictory fallback replies after partial delivery.
- **`WhatsAppChannel`:** Separated `queue_timeout_seconds` from `llm_timeout_seconds` (`float | None = 120.0`), enforced strict `2xx` outbound delivery (`follow_redirects=False`), added deterministic SHA-256 fallback `wamid` generation (`gen_<sha256>`), validated outbound/body-size settings with `ConfigurationError`, masked `sender` in webhook JSON responses, and supported all awaitable `on_24h_window_expired` hooks.

### Security
- **Credential Redaction and Sanitized Error Handling (from `0.4.0rc3`):** Shared credential-redaction pipeline across `OpenAIEngine`, `AnthropicEngine`, `GeminiEngine`, and `WhatsAppChannel` outbound logs (masking configured API keys, tokens, and embedded URL credentials across plain, JSON-escaped, and percent-encoded forms), sanitized `ProviderError` exceptions without chaining `httpx`/`json.JSONDecodeError` internals, pre-dispatch HTTP header credential validation, no credential-bearing redirects, and redacted/bounded `ToolArgumentValidationError` messages and tracebacks.

### Performance
- **Gemini Connection Pooling:** `async with runner:` reuses a pooled `httpx` client for `GeminiEngine` requests on the same event loop (opened automatically by `Runner.run()`, `TelegramChannel.run()`, and `WhatsAppChannel`).
- **Lower `SQLiteSessionStore` Query Overhead:** Single-transaction `SQLiteSessionStore.get()` and removal of redundant `refresh()` queries at turn start.

### Important Fixes
- **Prevent Synthetic Tool-Call ID Collisions Across Turns in `GeminiEngine`** ([#231](https://github.com/GustavoBaranda/chatflow-agent/issues/231), [#232](https://github.com/GustavoBaranda/chatflow-agent/pull/232)): when Gemini omits `functionCall.id` or returns `None`, `""`, or whitespace-only strings, `GeminiEngine` now generates a unique stateless Gemini-scoped fallback ID (`cf_gemini_<24 hex chars>`, 34 characters, compatible with OpenAI and Anthropic) instead of reusing per-response indices (`call_{name}_{part_idx}`). When sending history back to Gemini, `GeminiEngine` omits both current (`cf_gemini_<24 hex>`) and legacy (`call_{name}_{part_idx}`) Gemini synthetic IDs while preserving provider-supplied IDs and OpenAI/Anthropic IDs byte-for-byte.
- **Prevent Synthetic Tool-Call ID Collisions Across Turns in `OpenAIEngine`** ([#213](https://github.com/GustavoBaranda/chatflow-agent/issues/213), [#230](https://github.com/GustavoBaranda/chatflow-agent/pull/230)): when an OpenAI-compatible provider omits `tool_call.id` or returns `None`, `""`, or whitespace-only strings, `OpenAIEngine` now generates a unique stateless fallback ID (`call_<24 hex chars>`, 29 characters, compatible with OpenAI, Anthropic, and Gemini) instead of reusing per-response indices (`call_0`, `call_1`). Provider-supplied non-empty IDs remain unchanged byte-for-byte.
- **Configuration & Packaging Hardening:** Rejected boolean flags for `turn_timeout`, `queue_timeout_seconds`, `max_turns`, and `default_max_turns` ([#224](https://github.com/GustavoBaranda/chatflow-agent/pull/224)), constrained `httpx>=0.27.0,<1.0`, fell back to exponential backoff on invalid `Retry-After` headers across all engines/channels, and stopped remaining WhatsApp outbound chunks on failure with empty-reply fallback guarding.

### Breaking Changes from `0.3.x`
For full upgrade instructions and code examples, see the [0.4.0 Migration Guide](docs/MIGRATION_0.4.md). The four confirmed breaking changes from `v0.3.4` to `0.4.0` are:
1. **Removal of `google-genai` and end of Vertex AI / ADC fallback:** Core dependencies are now solely `pydantic>=2.6.0` and `httpx>=0.27.0,<1.0`; `GeminiEngine` calls the Gemini Developer REST API (`v1beta`) directly over `httpx` and requires an explicit Gemini API key instead of falling back to Google Cloud Vertex AI / Application Default Credentials (ADC).
2. **Removal of `GeminiEngine.client`:** The `GeminiEngine.client` attribute (previously a `google-genai` client) has been removed; pass `http_client: httpx.AsyncClient | None = None` or a custom `BaseEngine` stub instead.
3. **Rejection of duplicate `Agent` names:** Multi-agent graphs registering distinct `Agent` instances with the same `name` now raise an error instead of silently shadowing each other.
4. **Removal of `WhatsAppChannel` `dedup_ttl_hours` and keyword-only parameters:** Removed the unused `dedup_ttl_hours` parameter from `WhatsAppChannel` (configure deduplication TTL on the attached `SessionStore` / `SQLiteSessionStore`), and made `max_body_size`, `enable_docs`, and `queue_timeout_seconds` keyword-only.

### Notable Behavior Changes
- **Runtime tool-argument validation enabled by default:** Model-supplied tool arguments are validated and coerced via Pydantic (`ToolArgumentValidationError`, subclass of `ToolExecutionError`) before execution (`validate_args=True` by default, opt-out via `validate_args=False`).
- **Strict `Runner.run()` event-loop guard:** Calling synchronous `Runner.run()` inside an already running event loop raises `RuntimeError`; use `await runner.run_async(...)` in async contexts.

### Known Limitations
- **Historical persisted tool-call IDs:** New synthetic tool-call IDs generated in `0.4.0` are unique across turns, but existing SQLite sessions created before `0.4.0` remain untouched on disk for backward compatibility. As a result, legacy duplicated synthetic IDs (`call_0`, `call_{name}_{part_idx}`, or `""`) already present in historical SQLite sessions can still be propagated to Anthropic and OpenAI during cross-provider handoffs.
- **Single-node SQLite coordination:** `SQLiteSessionStore` is scoped to a single process/node; multi-node deployments require an application-provided `BaseSessionStore`.
- **WhatsApp at-most-once acknowledgment:** Recording `wamid` before background dispatch prevents duplicate processing at the deliberate cost of losing an in-flight turn if the process crashes immediately after acknowledging Meta's webhook.

## [0.4.0rc3] - 2026-11-22

### Security
- **Credential Redaction and Sanitized Error Handling Across Engines and WhatsApp Outbound Logs**: `OpenAIEngine`, `AnthropicEngine`, `GeminiEngine`, and `WhatsAppChannel` now use a shared credential-redaction pipeline that masks configured API keys, tokens, and embedded URL credentials (across plain, JSON-escaped, and percent-encoded forms) before error bodies are truncated or written to logs, while preserving non-sensitive HTTP diagnostic details. Network, invalid-URL, HTTP client creation, and malformed JSON failures in `OpenAIEngine`, `AnthropicEngine`, and `GeminiEngine` now raise sanitized `ProviderError` exceptions without chaining underlying `httpx` or `json.JSONDecodeError` instances (`__cause__` and `__context__` are `None`), preserving HTTP status codes and exception type names. Non-empty HTTP header credentials containing spaces, control characters, or non-ASCII characters are validated and rejected before dispatching requests.

### Fixed
- **Bound `TelegramChannel` `RetryAfter` Flood-Control Wait Time (`max_retry_after_seconds`)** ([#211](https://github.com/GustavoBaranda/chatflow-agent/issues/211)): `TelegramChannel` now accepts keyword-only `max_retry_after_seconds: float = 60.0` (validated with `ConfigurationError`, rejecting booleans, negative values, and non-finite numbers). The cap applies per `RetryAfter` event (not as a global turn or delivery timeout: up to 3 retries per chunk can still accumulate up to 180s of sleep per chunk excluding HTTP time, plus additional wait across chunks). Delays above the cap abort immediately without sleeping or retrying, without duplicating already-sent chunks or appending `fallback_message` after partial delivery (`0.0` allows zero-second delays and rejects positive waits). This changes previous behavior for `RetryAfter` delays above 60s.
- **Reject Non-2xx Outbound WhatsApp Responses** ([#210](https://github.com/GustavoBaranda/chatflow-agent/issues/210)): `WhatsAppChannel._send_single_outbound_whatsapp()` now passes `follow_redirects=False` explicitly and treats only `2xx` (`200 <= status_code < 300`) responses as successful delivery. `3xx` redirect responses are logged with the masked recipient phone number, return `False` without retrying, and stop any remaining chunks in multi-chunk replies.
- Reject boolean flags for `turn_timeout`, `queue_timeout_seconds`, `max_turns` and `default_max_turns` with the existing `ValueError` contract ([#224](https://github.com/GustavoBaranda/chatflow-agent/pull/224) by [@jwalith4418-Mj](https://github.com/jwalith4418-Mj), [#214](https://github.com/GustavoBaranda/chatflow-agent/issues/214)). Positive numeric settings and `turn_timeout=None` are unchanged.

- **New Public Exception `ConfigurationError`** (subclass of `ChatFlowError` and `ValueError`) ([#183](https://github.com/GustavoBaranda/chatflow-agent/pull/183) by [@GustavoBaranda](https://github.com/GustavoBaranda), [#166](https://github.com/GustavoBaranda/chatflow-agent/issues/166)): exported from `chatflow_agent`.
- **New Public Exception `ToolArgumentValidationError`** (subclass of `ToolExecutionError`) ([#160](https://github.com/GustavoBaranda/chatflow-agent/pull/160) by [@GustavoBaranda](https://github.com/GustavoBaranda)): exported from `chatflow_agent`.
- **Runtime Tool Argument Validation (`ToolArgumentValidationError`)** ([#160](https://github.com/GustavoBaranda/chatflow-agent/pull/160) by [@GustavoBaranda](https://github.com/GustavoBaranda)): Tools validate LLM-provided arguments at runtime prior to execution against parameter type annotations using Pydantic (`validate_args=True` by default). String parameters accept coerced integers and floats (excluding booleans), while boolean parameters follow standard boolean coercion (accepting native booleans, common logical string representations like `"true"`/`"false"`, and integers `0` and `1`). Numeric types enforce finite values (`allow_inf_nan=False`) and reject booleans. Parameters with default `None` accept `None` and omitted values, reflected as `nullable: true` in Gemini OpenAPI 3.0 schemas and as `null` types / `anyOf` in OpenAI/Anthropic JSON Schemas. Non-schema annotations retain fallback types (`STRING` in Gemini, `string` in OpenAI) and are validated as `Any`. Supports parameters with leading underscores (`_id`) or named `model_config`, preserves Python call semantics for all parameter kinds, and retains native parameter binding for omitted arguments with mutable defaults. Validation can be configured per tool (`validate_args=False`) and isolates shared tool configurations across agents.

### Fixed
- **Pin Compatible `httpx<1.0` Range and PyPI Packaging Metadata** ([#202](https://github.com/GustavoBaranda/chatflow-agent/issues/202)): constrained `httpx` in `pyproject.toml` to `>=0.27.0,<1.0` so prerelease installations cannot resolve incompatible `httpx` 1.x development releases (such as `httpx==1.0.dev6` where `httpx.AsyncClient` is absent), updated the PyPI development status classifier from `Alpha` to `Beta`, and switched the README logo image sources to absolute raw GitHub URLs so they render reliably on both GitHub and PyPI.
- **Accurate `llm_timeout_seconds` Type Annotation on `WhatsAppChannel`** ([#200](https://github.com/GustavoBaranda/chatflow-agent/issues/200)): `WhatsAppChannel.__init__` and `WhatsAppChannel.llm_timeout_seconds` are now annotated as `float | None = 120.0` instead of `float = 120.0`, matching the documented and runtime behavior where `None` disables the turn timeout. Static type checkers (`mypy`, `pyright`) now accept `WhatsAppChannel(..., llm_timeout_seconds=None)` without changing runtime behavior. CI verifies this in `tests/type_checks/whatsapp.py` with `mypy --strict tests/type_checks`.
- **Stable Fallback `wamid` for Meta WhatsApp Messages Without an `id`** ([#175](https://github.com/GustavoBaranda/chatflow-agent/issues/175)): when a Meta Cloud API webhook message item omits `"id"`, `WhatsAppChannel._extract_messages()` now derives the fallback `wamid` (`gen_<sha256>`) from the SHA-256 digest of the canonical JSON representation (`sort_keys=True`, compact separators) instead of Python's per-process randomized `hash(str(msg))`. Deduplication of such messages is now deterministic across key reorderings and process restarts, while real WhatsApp message IDs and generic webhook behavior remain unchanged.
- **Telegram Flood-Control Retry and Guarded Fallback Send** ([#175](https://github.com/GustavoBaranda/chatflow-agent/issues/175)): `TelegramChannel` now catches `telegram.error.RetryAfter` when sending reply chunks, waits asynchronously for the requested flood-control delay (clamped to a finite non-negative duration), and retries only the unsent chunk up to 3 times instead of immediately falling through to the error handler. Already-sent chunks are never duplicated, and if a send fails after partial content has already been delivered (or after flood-control retries are exhausted), the channel stops without appending a contradictory `fallback_message`. Sending `fallback_message` on pre-delivery errors is now guarded so a secondary send failure is logged rather than escaping unhandled from `_handle_message`, and handler error logs record only the exception class name (`type(err).__name__`) instead of raw exception messages.
- **WhatsApp Outbound and Body-Size Settings Are Validated** ([#198](https://github.com/GustavoBaranda/chatflow-agent/pull/198) by [@MbappeWU](https://github.com/MbappeWU), [#175](https://github.com/GustavoBaranda/chatflow-agent/issues/175)): `WhatsAppChannel` now rejects invalid outbound retry and webhook body-size settings at construction with `ConfigurationError` (a `ValueError` subclass). `max_outbound_retries` must be an integer from 0 to 10; `outbound_base_delay` and `outbound_max_delay` must be finite real numbers greater than or equal to zero; and `max_body_size` must be a positive integer. Booleans are rejected for all four settings. Defaults, zero retries, zero delays, and a maximum delay below the base delay remain valid. Configurations that relied on invalid values, including float body sizes such as `2e6`, now fail fast instead of causing broken backoff or payload limits at runtime.
- **Documentation Matches the Implementation** ([#172](https://github.com/GustavoBaranda/chatflow-agent/issues/172)):
  - the Architecture Guide no longer claims that `GeminiEngine` merges consecutive turns or preserves `thoughtSignature`, and its exception tree now includes `ToolArgumentValidationError` and `JsonCodecError`;
  - the Migration Guide gives the real `replacement_tool_call_id(call_id)` signature and no longer states that `Agent.provider` defaults to `"gemini"` (it defaults to `None`);
  - the READMEs limit WAL to file-backed SQLite stores (`":memory:"` stores do not use WAL) and list the `text-embedding-` and `dall-e` model prefixes;
  - `SECURITY.md` lists `0.4.0` pre-releases as intended for testing and evaluation, without guaranteed backports or response times (`0.3.4` remains the supported stable release), and has the same closing note in English and Spanish;
  - both READMEs show the project logo for GitHub's light and dark themes, credit the verified contributors `dannyward630` and `IENVYshanks`, and fix the in-page links to the Contributing and Support sections.

  English and Spanish versions were updated together.
- **WhatsApp `on_24h_window_expired` Runs for Every Async Callable** ([#196](https://github.com/GustavoBaranda/chatflow-agent/pull/196) by [@GustavoBaranda](https://github.com/GustavoBaranda), [#175](https://github.com/GustavoBaranda/chatflow-agent/issues/175)): the hook was classified with `asyncio.iscoroutinefunction`, which does not recognize objects with an `async __call__`, `functools.partial` wrappers of them, or plain functions that return a coroutine. For those hooks the coroutine was created but never awaited, so the hook silently never ran and Python emitted `RuntimeWarning: coroutine ... was never awaited`. The channel now calls the hook and awaits its result whenever it is awaitable, which also removes the use of `asyncio.iscoroutinefunction`, deprecated in Python 3.14. `async def` hooks and synchronous hooks behave as before: synchronous hooks still run inline on the event loop and must not block, and exceptions raised by any hook are still logged and do not interrupt outbound delivery.
- **Invalid `Retry-After` Headers Fall Back to Exponential Backoff** ([#194](https://github.com/GustavoBaranda/chatflow-agent/pull/194) by [@MbappeWU](https://github.com/MbappeWU), [#175](https://github.com/GustavoBaranda/chatflow-agent/issues/175)): negative or non-finite `Retry-After` values in `WhatsAppChannel` outbound retries, `OpenAIEngine`, and `AnthropicEngine` are now treated as invalid and fall back to exponential backoff instead of triggering an immediate retry, matching `GeminiEngine`.
- **Mask Sender Phone Number in WhatsApp Webhook JSON Responses** ([#192](https://github.com/GustavoBaranda/chatflow-agent/pull/192) by [@MbappeWU](https://github.com/MbappeWU), [#175](https://github.com/GustavoBaranda/chatflow-agent/issues/175)): `WhatsAppChannel` now masks the `sender` field in webhook JSON responses with `_mask_phone()`, matching log redaction so raw phone numbers are not exposed to reverse proxies or APM tools.
- **Plain Functions With `self`/`cls` Parameters Kept in Tool Schemas** ([#191](https://github.com/GustavoBaranda/chatflow-agent/pull/191) by [@MbappeWU](https://github.com/MbappeWU), [#176](https://github.com/GustavoBaranda/chatflow-agent/issues/176)): `Tool` no longer strips parameters named `self` or `cls` from schemas or argument validators via GC/method heuristics; `Tool.execute()`, `execute_async()`, and `__call__()` make `self` positional-only so keyword arguments named `self` reach the wrapped callable. Instance and class methods should be passed as bound methods.
- **Consistent JSON Encoding for Tool Results and Session Metadata** ([#188](https://github.com/GustavoBaranda/chatflow-agent/pull/188) by [@MbappeWU](https://github.com/MbappeWU), [#167](https://github.com/GustavoBaranda/chatflow-agent/issues/167)): unified JSON serialization across engines and session stores via `json_codec`, encoding `datetime`/`date`/`time` values as ISO-8601. Session metadata serialization fails fast with `JsonCodecError` on unsupported objects, while tool-result wire encoding preserves string coercion for non-JSON leaf values.
- **Stop WhatsApp Outbound Chunks on Failure and Guard Empty Replies** ([#180](https://github.com/GustavoBaranda/chatflow-agent/pull/180) by [@MbappeWU](https://github.com/MbappeWU), [#169](https://github.com/GustavoBaranda/chatflow-agent/issues/169)): `WhatsAppChannel` now stops sending remaining reply chunks as soon as one chunk fails instead of continuing delivery; empty or whitespace-only replies send `fallback_message` on both `WhatsAppChannel` and `TelegramChannel`; and `WhatsAppChannel` logs a warning at construction when `access_token` or `phone_number_id` is missing.
- **Honor `Agent(api_key=...)` on Default Gemini Fallback** ([#179](https://github.com/GustavoBaranda/chatflow-agent/pull/179) by [@GustavoBaranda](https://github.com/GustavoBaranda), [#163](https://github.com/GustavoBaranda/chatflow-agent/issues/163)): when an `Agent` specifies `api_key=...` without an explicit `engine`, `provider`, or `base_url` and `resolve_engine()` falls back to a plain `GeminiEngine`, it now returns a copy configured with the agent's key while preserving all other engine settings.
- **Precise Static Types for `tool()` and `Agent.tool()`** ([#195](https://github.com/GustavoBaranda/chatflow-agent/pull/195) by [@GustavoBaranda](https://github.com/GustavoBaranda), [#176](https://github.com/GustavoBaranda/chatflow-agent/issues/176)): both decorators were annotated as returning `Any`, so type checkers lost the type of every decorated tool and `mypy --strict` reported "Untyped decorator makes function … untyped" for the parameterized forms. `@overload` signatures now declare what they return at runtime: `@tool` / `@agent.tool` return a `Tool`, and the parameterized forms (`@tool()`, `@tool("name")`, `@tool(name=...)`, `@agent.tool(...)`) return a decorator that produces a `Tool`. Runtime behavior is unchanged. For mypy users: invalid attribute access on a decorated tool is now reported, and existing `# type: ignore[untyped-decorator]` comments may become unused, which `--strict` reports through `warn_unused_ignores`. CI checks these types with `mypy --strict tests/type_checks/decorators.py`.
- **Prevent Silent Provider and Endpoint Fallbacks** ([#183](https://github.com/GustavoBaranda/chatflow-agent/pull/183) by [@GustavoBaranda](https://github.com/GustavoBaranda), [#166](https://github.com/GustavoBaranda/chatflow-agent/issues/166)): an explicitly configured provider on an `Agent` is now validated strictly against the supported provider set (`gemini`, `google`, `openai`, `grok`, `xai`, `deepseek`, `groq`, `ollama`, `gemma`, `anthropic`, `claude`); unsupported providers (such as `"mistral"`) raise `ConfigurationError` immediately instead of silently falling through to model-prefix heuristics and unintended local endpoints. Combining `provider="gemini"` or `"google"` with `base_url` raises `ConfigurationError` rather than silently ignoring the endpoint (custom Gemini endpoints must use the `GOOGLE_GEMINI_BASE_URL` environment variable). Custom remote endpoints without an `api_key` raise `ConfigurationError` early at `Runner` initialization rather than failing mid-turn as a plain `ValueError`. `OpenAIEngine(provider=...)` with an unrecognized provider without an explicit `base_url` raises `ConfigurationError` instead of falling back to OpenAI. Unrecognized model prefixes without an explicit provider preserve their documented fallback to Gemini.
- **Union Arguments Ignore Member Order** ([#178](https://github.com/GustavoBaranda/chatflow-agent/pull/178) by [@bfs2021](https://github.com/bfs2021), [#168](https://github.com/GustavoBaranda/chatflow-agent/issues/168)): runtime argument validation no longer turns an integer into a string merely because `str` was written first in `str | int`. The sanitized union now tries the members that do not coerce before `str`, so a value that already matches a member exactly is delivered unchanged, while the number-to-string coercion still applies when no other member accepts the value. This changes the delivered value for tools annotated `str | int` that previously received `"5"`: they now receive `5`.
- **In-Memory Session Metadata Isolation** ([#177](https://github.com/GustavoBaranda/chatflow-agent/pull/177) by [@dannyward630](https://github.com/dannyward630), [#162](https://github.com/GustavoBaranda/chatflow-agent/issues/162)): in-memory sessions deep-copy metadata when created. Sessions initialized from the same mapping no longer share nested values with each other or the caller; turn metadata, handoff updates, and failed-turn rollback preserve that isolation. SQLite serialization is unchanged. Callers that relied on mutating the original mapping to update a live session should use `SessionContext.update_metadata()`.
- **Thread-Safe In-Memory `SessionStore` Deduplication** ([#147](https://github.com/GustavoBaranda/chatflow-agent/pull/147) by [@GustavoBaranda](https://github.com/GustavoBaranda)): `SessionStore.record_processed_message()` and `is_message_processed()` are guarded by an internal lock, so concurrent threads sharing one in-memory store can no longer both accept the same message id. Expiration, purge and capacity semantics are unchanged, as are `SQLiteSessionStore`, `Runner` and channel behavior. (REC-01 of the `v0.4.0rc1` stabilization audit.)
- **Tool Argument Validation Traceback & Exception Redaction** ([#160](https://github.com/GustavoBaranda/chatflow-agent/pull/160) by [@GustavoBaranda](https://github.com/GustavoBaranda)): `ToolArgumentValidationError` sanitizes built-in validation errors to prevent leaking raw user inputs, API keys, untrusted model-supplied keys, or nested paths in `str(exc)`, `repr(exc)`, `exc.args`, and exception tracebacks (`__cause__` and `__context__` are strictly suppressed). Error counts (max 3) and total message length (max 300 characters) are strictly bounded. Exceptions explicitly raised by custom user-defined validators are not guaranteed to redact inputs embedded by user code.

### ⚠ BREAKING CHANGES
1. **`GeminiEngine` Uses the Gemini REST API over `httpx`; `google-genai` Removed and Vertex AI No Longer Supported** ([#130](https://github.com/GustavoBaranda/chatflow-agent/pull/130) by [@Gokulnaath07](https://github.com/Gokulnaath07), [#116](https://github.com/GustavoBaranda/chatflow-agent/issues/116)): `GeminiEngine` now calls the Gemini Developer API (Google AI Studio) over REST with an API key, and `google-genai` is no longer a dependency of chatflow-agent (the core runtime dependencies are `pydantic` and `httpx`). Application Default Credentials and the `GOOGLE_GENAI_USE_VERTEXAI`, `GOOGLE_CLOUD_PROJECT` and `GOOGLE_CLOUD_LOCATION` variables, which `google-genai` could use, are ignored; such setups now fail with `ProviderError("Gemini API client is not configured. ...")`. Use a Gemini API key (`GEMINI_API_KEY`, `GOOGLE_API_KEY` or `api_key=...`), or provide your own `BaseEngine` through `Runner(engine=...)`.
2. **`GeminiEngine.client` Removed** ([#130](https://github.com/GustavoBaranda/chatflow-agent/pull/130) by [@Gokulnaath07](https://github.com/Gokulnaath07), [#116](https://github.com/GustavoBaranda/chatflow-agent/issues/116)): the attribute held the `google.genai.Client` (or `None` if it could not be created) and no longer exists. Reading it raises `AttributeError`; assigning it (e.g. a fake client in a test) raises nothing but has no effect, so requests then go to the real API. Migration:
   - **Calling the SDK directly** (e.g. listing models or uploading files): install `google-genai` yourself and create your own `genai.Client`.
   - **Mocking Gemini in tests or customizing HTTP** (proxies, TLS, transports): pass an `httpx.AsyncClient` with `GeminiEngine(http_client=...)`, for example `httpx.AsyncClient(transport=httpx.MockTransport(handler))`, and use the engine through `Runner(engine=...)` (pass the key to `GeminiEngine(api_key=...)` or set `GEMINI_API_KEY`; `Runner(api_key=...)` is then not used). Responses follow the Gemini REST API (`generateContent`), not the SDK's objects. The client belongs to the caller: chatflow-agent never closes it, and it must be used on one event loop only, so it does not suit `Runner.run()` or `CLIChannel`, which start a new event loop per call.
3. **Distinct `Agent` Instances With the Same Name Are Rejected** ([#128](https://github.com/GustavoBaranda/chatflow-agent/pull/128) by [@MbappeWU](https://github.com/MbappeWU), co-authored by [@GustavoBaranda](https://github.com/GustavoBaranda), [#123](https://github.com/GustavoBaranda/chatflow-agent/issues/123)): building a `Runner` whose handoff graph contains two distinct `Agent` instances with the same `name` now raises `ValueError`; previously the second instance was silently ignored and its handoffs went to the first one. The same check applies to `add_handoff()` after initialization and to `register_agent()`; a rejected change leaves the registry untouched. Reusing one `Agent` instance on several branches, or in cycles, keeps working. Give each distinct agent a unique name.

### Changed
- **WhatsApp Timeouts: Queue and Turn Are Limited Separately** ([#93](https://github.com/GustavoBaranda/chatflow-agent/pull/93) by [@dbdefault](https://github.com/dbdefault), [#91](https://github.com/GustavoBaranda/chatflow-agent/issues/91); [#131](https://github.com/GustavoBaranda/chatflow-agent/pull/131) by [@GustavoBaranda](https://github.com/GustavoBaranda)): the default `llm_timeout_seconds` rose from 30 to 120 seconds, and it now bounds only the turn, starting once it holds the session; the wait for the session is bounded by `queue_timeout_seconds`. A reply can therefore take up to `queue_timeout_seconds + llm_timeout_seconds` (240 s with the defaults). A message whose wait expires gets `fallback_message` and its turn never runs. A custom `dispatch_async()` that does not call `Runner.run_async()` is bounded by that sum plus one second. `None` and `inf` still set no turn limit and zero or negative values still time every turn out; `nan` now sets no limit (it used to time turns out at once or, on Python 3.13, stop the event loop). Zero, negative and `nan` values log a warning.
- **WhatsApp Timeout Logs** ([#131](https://github.com/GustavoBaranda/chatflow-agent/pull/131) by [@GustavoBaranda](https://github.com/GustavoBaranda)): the single `LLM dispatch timed out ...` error is replaced by `Session busy ...` (queue limit), `Turn timed out ...` (turn limit), `Dispatch backstop expired ...` (a `dispatch_async()` that never reached `Runner.run_async()`) and `TimeoutError raised while dispatching ...` (a `TimeoutError` raised by the provider or other code). Update alerts that match the old text.
- **Turns Started From Inside a Turn Raise** ([#120](https://github.com/GustavoBaranda/chatflow-agent/pull/120) by [@GustavoBaranda](https://github.com/GustavoBaranda), [#31](https://github.com/GustavoBaranda/chatflow-agent/issues/31)): calling `Runner.run_async()` or `Runner.run()` for a session from code started by a running turn of that same session (a tool, or any task or thread it starts: `create_task`, `gather`, `wait_for`, `TaskGroup`, `asyncio.to_thread`) now raises `ReentrantTurnError` immediately. Previously these calls waited forever (in-memory store) or ran unserialized alongside the outer turn (SQLite). Use `Runner.spawn_turn()` for follow-up turns. This applies to every session store, including custom ones.
- **SQLite Turns Run One at a Time, in Arrival Order** ([#120](https://github.com/GustavoBaranda/chatflow-agent/pull/120), [#133](https://github.com/GustavoBaranda/chatflow-agent/pull/133) by [@GustavoBaranda](https://github.com/GustavoBaranda)): concurrent requests for the same SQLite session are processed sequentially, so a queued request waits for the previous turn. With a file-backed store a turn takes the session lock before loading the session, so turns start in the order they arrive. A turn running when its session is deleted always fails with `SessionDeletedError`.
- **Cancelled Turns Wait for Their Running SQLite Write** ([#133](https://github.com/GustavoBaranda/chatflow-agent/pull/133) by [@GustavoBaranda](https://github.com/GustavoBaranda)): cancelling a turn, or reaching its `turn_timeout`, while one of its SQLite writes is running waits until that write ends, then rolls the turn back, and only then raises; the session stays locked meanwhile. The `TimeoutError` (and the WhatsApp fallback reply) can therefore arrive later: up to SQLite's `busy_timeout` (10 s; somewhat longer on Windows) per pending write while another writer holds the database. A write that has not started yet is withdrawn instead. If the rollback itself fails, its error is raised and logged (`Rolling back the failed turn of session ... failed`); the turn is never reported as rolled back.
- **`GeminiEngine` Retry Delays Are Bounded by `max_delay`** ([#130](https://github.com/GustavoBaranda/chatflow-agent/pull/130) by [@Gokulnaath07](https://github.com/Gokulnaath07), [#116](https://github.com/GustavoBaranda/chatflow-agent/issues/116)): on a 429, 500, 502, 503 or 504 response, a `Retry-After` header (seconds, or an HTTP-date in any of the three formats HTTP allows) replaces the exponential backoff, but the wait never exceeds `max_delay` (10 s by default). A malformed value (for example `soon`, `-5`, `nan` or an invalid date) is ignored and the exponential backoff applies.
- **Unsupported Tool Parameter Types Fail at Registration** ([#118](https://github.com/GustavoBaranda/chatflow-agent/pull/118) by [@rahul05ranjan](https://github.com/rahul05ranjan), [#115](https://github.com/GustavoBaranda/chatflow-agent/issues/115)): a tool parameter with a union annotation that contains a member with no concrete JSON Schema mapping now raises `ToolSchemaError` when the tool is created, instead of being silently declared as a string; annotations outside unions that cannot be expressed keep the previous `STRING` (Gemini) / `string` (OpenAI) fallback.
- **Stricter Input Validation:** `Runner.run()` called from a running event loop raises a `RuntimeError` that points to `await runner.run_async(...)` ([#57](https://github.com/GustavoBaranda/chatflow-agent/pull/57) by [@ompatil1906](https://github.com/ompatil1906), [#56](https://github.com/GustavoBaranda/chatflow-agent/issues/56)); empty or whitespace-only `Agent` names raise `ValueError` ([#86](https://github.com/GustavoBaranda/chatflow-agent/pull/86) by [@jay23606](https://github.com/jay23606), [#84](https://github.com/GustavoBaranda/chatflow-agent/issues/84)); non-positive `max_turns` / `default_max_turns` in session contexts and stores raise `ValueError` ([#63](https://github.com/GustavoBaranda/chatflow-agent/pull/63) by [@sarantez](https://github.com/sarantez), [#59](https://github.com/GustavoBaranda/chatflow-agent/issues/59)); `split_message()` with `max_len <= 0` raises `ValueError` instead of looping forever ([#46](https://github.com/GustavoBaranda/chatflow-agent/pull/46) by [@krishna2707](https://github.com/krishna2707), [#45](https://github.com/GustavoBaranda/chatflow-agent/issues/45)).
- **WhatsApp HTTP 413 Status** ([#136](https://github.com/GustavoBaranda/chatflow-agent/pull/136) by [@GustavoBaranda](https://github.com/GustavoBaranda)): `WhatsAppChannel` no longer references Starlette's deprecated `HTTP_413_REQUEST_ENTITY_TOO_LARGE` constant; oversized bodies are still rejected with HTTP 413.

### Fixed
- **Overlapping Synchronous Tools After Turn Timeout** ([#142](https://github.com/GustavoBaranda/chatflow-agent/pull/142) by [@GustavoBaranda](https://github.com/GustavoBaranda)): when a synchronous tool (`def`) running via `asyncio.to_thread()` exceeds `turn_timeout`, its worker thread continues running in the background due to Python thread runtime constraints. The session lock barrier now tracks the running synchronous tool ticket and waits up to `queue_timeout_seconds` before allowing subsequent turns of the same session to acquire the lock. If the worker thread attempts to invoke a nested turn on the same session while draining, it is rejected immediately with `ReentrantTurnError`.
- **SQLite Session Integrity Under Concurrent Requests** ([#120](https://github.com/GustavoBaranda/chatflow-agent/pull/120) by [@GustavoBaranda](https://github.com/GustavoBaranda), [#31](https://github.com/GustavoBaranda/chatflow-agent/issues/31)): turns for the same `session_id` on a `SQLiteSessionStore` now share one lock per event loop; previously every request got its own lock and turns ran in parallel. Each turn reloads the history, active agent and metadata committed by earlier turns after acquiring the lock. A failed or cancelled turn no longer deletes or overwrites what someone else committed meanwhile: it then reverts only its own changes, in a single `BEGIN IMMEDIATE` transaction, and logs a warning. The lock registry holds locks weakly and creates separate locks per event loop, so successive `Runner.run()` calls keep working.
- **SQLite No Longer Blocks the Event Loop** ([#133](https://github.com/GustavoBaranda/chatflow-agent/pull/133) by [@GustavoBaranda](https://github.com/GustavoBaranda)): with a file-backed `SQLiteSessionStore`, the Runner's session calls, the WhatsApp webhook's deduplication write and Telegram's `/reset` run in a small pool of worker threads owned by the store (4 threads, created on first use, shut down by `close()`). A slow disk or a database locked by another writer no longer stops every webhook, session and timeout of the process. `SessionStore`, `:memory:` SQLite stores, subclasses of `SQLiteSessionStore` and custom stores still run on the event loop.
- **Atomic WhatsApp Deduplication on SQLite** ([#120](https://github.com/GustavoBaranda/chatflow-agent/pull/120) by [@GustavoBaranda](https://github.com/GustavoBaranda)): `SQLiteSessionStore.record_processed_message()` checks and records a message id in a single statement, so two concurrent deliveries of the same `wamid` can no longer both be processed. Requires SQLite 3.24 or later.
- **Deleted Sessions No Longer Get Orphan Messages** ([#120](https://github.com/GustavoBaranda/chatflow-agent/pull/120) by [@GustavoBaranda](https://github.com/GustavoBaranda)): a turn that is running when its SQLite session is deleted fails with `SessionDeletedError` instead of storing its reply without a session. A turn waiting for a deleted session starts a new, empty one; deleted content is never restored.
- **Complete Rollback of Failed Turns:** a failed turn restores messages pruned during the turn ([#34](https://github.com/GustavoBaranda/chatflow-agent/pull/34) by [@KeuqS](https://github.com/KeuqS), [#32](https://github.com/GustavoBaranda/chatflow-agent/issues/32)), the active agent and the metadata ([#52](https://github.com/GustavoBaranda/chatflow-agent/pull/52) by [@aazminu](https://github.com/aazminu), [#51](https://github.com/GustavoBaranda/chatflow-agent/issues/51)), also when the turn is cancelled ([#69](https://github.com/GustavoBaranda/chatflow-agent/pull/69) by [@Aaqibhafeezkhan](https://github.com/Aaqibhafeezkhan), [#60](https://github.com/GustavoBaranda/chatflow-agent/issues/60)).
- **Session Metadata Persistence:** `Handoff.context_updates` is stored when a handoff happens ([#41](https://github.com/GustavoBaranda/chatflow-agent/pull/41) by [@mikemikimike](https://github.com/mikemikimike), [#37](https://github.com/GustavoBaranda/chatflow-agent/issues/37)), and metadata passed to `run_async()` is persisted on every turn ([#95](https://github.com/GustavoBaranda/chatflow-agent/pull/95) by [@Erfouni](https://github.com/Erfouni), [#89](https://github.com/GustavoBaranda/chatflow-agent/issues/89)).
- **Handoffs:** handoffs resolve to the peer the current agent declares, so same-named specialists on different branches no longer steal each other's handoffs ([#128](https://github.com/GustavoBaranda/chatflow-agent/pull/128) by [@MbappeWU](https://github.com/MbappeWU), [#123](https://github.com/GustavoBaranda/chatflow-agent/issues/123)); handoffs added with `add_handoff()` after the `Runner` was created are resolved ([#112](https://github.com/GustavoBaranda/chatflow-agent/pull/112) by [@dbdefault](https://github.com/dbdefault), [#105](https://github.com/GustavoBaranda/chatflow-agent/issues/105)); user tools are kept when a handoff tool name collides with them ([#49](https://github.com/GustavoBaranda/chatflow-agent/pull/49) by [@jsdhwfmax](https://github.com/jsdhwfmax), [#48](https://github.com/GustavoBaranda/chatflow-agent/issues/48)); non-ASCII agent names produce distinct handoff tool names ([#108](https://github.com/GustavoBaranda/chatflow-agent/pull/108) by [@dbdefault](https://github.com/dbdefault), [#104](https://github.com/GustavoBaranda/chatflow-agent/issues/104)); reaching `max_handoffs_per_turn` still returns a result for every tool call ([#50](https://github.com/GustavoBaranda/chatflow-agent/pull/50) by [@jsdhwfmax](https://github.com/jsdhwfmax), [#27](https://github.com/GustavoBaranda/chatflow-agent/issues/27)).

### Known Issues
- **Concurrency Scope:** Serialization is not provided across store instances on the same file, across processes, or across threads running their own event loops.
- **Nested Turns Outside the Turn's Tasks:** a tool that waits for work done by a task that was not started from the turn (for example, a worker created earlier) can still deadlock if that work runs a turn of the same session. Awaiting a task returned by `spawn_turn()` inside the turn that spawned it deadlocks as well.
- **SQLite Contention Still Delays the Requests That Need the Database:** an SQLite call that has started cannot be interrupted. While another writer holds the database, the WhatsApp webhook still acknowledges only after its deduplication write (at-most-once semantics are unchanged), so that HTTP response waits; if the lock lasts longer than `busy_timeout`, that webhook fails with HTTP 500 and, since the message was not recorded, Meta's retry is processed. Shutting down can wait for SQLite calls still running. Several workers or processes on one SQLite file are still not supported: running SQLite outside the event loop does not coordinate processes.
- **Reset and Delete During a Turn:** `clear_history()` and `delete()` are not coordinated with running turns beyond the rollback and `SessionDeletedError` guarantees above (tracked separately).

## [0.3.0] - 2026-09-21

### Security
- **WhatsApp Webhook Signature Verification Enforced (SEC-01):** Fixed vulnerability where inbound POST `/webhook` requests were processed without verifying Meta's `X-Hub-Signature-256` HMAC header, allowing unauthenticated attackers to forge messages. `WhatsAppChannel` now enforces a strict fail-closed policy: `app_secret` is required by default, validating requests with constant-time `hmac.compare_digest` and rejecting invalid or missing signatures with HTTP 403.
- **Timing Attack Mitigation (SEC-02):** GET `/webhook` challenge verification now uses constant-time `hmac.compare_digest` for verify tokens.
- **Credential Masking in Logs:** Sensitive tokens, app secrets, and credentials are automatically redacted across all logging handlers.
- **Fail-Closed Starter Templates:** Example scripts (`whatsapp_service.py`, `whatsapp_persistent_bot.py`) raise `RuntimeError` if `WHATSAPP_APP_SECRET` is unset rather than falling back to an insecure development secret.

### ⚠ BREAKING CHANGES
1. **`WhatsAppChannel` requires `app_secret` by default (SEC-01):** Omitting `app_secret` raises `ValueError` on startup unless `verify_signature=False` is explicitly set (local testing only).
2. **Webhook response payload changed (BUS-01):** POST `/webhook` returns `{"status":"success","sender":"...","messages_queued": N}`. Inference and messaging are now dispatched asynchronously in background tasks.
3. **`max_turns` counts complete user conversation turns (DATA-01):** `max_turns` now enforces complete user dialogue turns (user message + model responses + tool results) rather than individual message objects.

### Added / Fixed
- **Background Webhook Dispatch (BUS-01):** Webhooks respond HTTP 200 to Meta immediately, preventing timeout retries on slow LLM calls.
- **At-Most-Once Deduplication (ARCH-01):** Atomic message ID tracking in SQLite with an 8-day TTL (`DEFAULT_DEDUP_TTL_HOURS = 192`) safely discards Meta retries.
- **Multi-Message Batch Extraction:** Webhooks with multiple message payloads are unpacked and dispatched independently.
- **Selective Outbound Retry Backoff with Jitter:** Outbound HTTP retries are strictly limited to `ConnectError`, `ConnectTimeout`, and HTTP 429, honoring the `Retry-After` header.
- **Meta 24h Window Expiration Handling:** Detects Meta error code `131047`, executes optional `on_24h_window_expired` callback safely (try/except), and logs masked recipient numbers.
- **Outbound Message Splitting:** Messages exceeding Meta's 4,096-character limit are automatically split across paragraph and sentence boundaries into sequential chunks.
- **Mid-Turn Failure Rollback:** Automatically reverts dialogue history to the last consistent turn in memory and SQLite on mid-turn engine failure and guarantees fallback delivery to WhatsApp.
- **Turn-Based Pruning & Memory Integrity (DATA-01):** FIFO pruning preserves system prompts and atomic tool call/result pairs.
- **SQLite Concurrency & WAL Mode:** Configured `PRAGMA busy_timeout = 10000` and `PRAGMA journal_mode = WAL` for atomic multi-reader concurrency. Existing databases transition automatically without schema recreation.
- **Documentation Parity:** 100% bilingual parity across README and CHANGELOG.

### Migration Guide
If you are upgrading from v0.2.0:
1. **Set `WHATSAPP_APP_SECRET`:** Add your Meta App Secret to your environment variables and pass it to `WhatsAppChannel(..., app_secret=os.environ["WHATSAPP_APP_SECRET"])`. For local testing without signature validation, explicitly pass `verify_signature=False`.
2. **Update Webhook Payload Parsing:** If any internal client monitored the POST `/webhook` response body, update it to expect `{"status": "success", "messages_queued": N}` instead of the synchronous `reply` field.
3. **Reduce `max_turns` Setting:** If your configuration previously used inflated `max_turns` values to account for individual messages (e.g. `max_turns=40` which held ~10 real turns), reduce it to the number of full turns you actually want to retain (e.g., lower to `max_turns=10`). Keeping the old number will retain roughly 4x more context than before.

### Funcionalidades Nuevas y Destacados
- **Timeouts por turno, turnos diferidos y reset seguro de sesiones:** Se agregaron `Runner.run_async(..., turn_timeout=...)`, `Runner.spawn_turn()` para encolar turnos de seguimiento fuera del candado activo, `Runner.reset_session_async()` / `Runner.reset_session()`, `SessionContext.refresh()` y `/reset` en `CLIChannel`.

### Motores y Proveedores
- **`GeminiEngine` nativo sobre `httpx`:** Reemplazo del SDK `google-genai` por solicitudes directas a la API REST de Gemini Developer (`v1beta`) sobre `httpx`, con soporte para `http_client=...`, `api_key_in_query=True`, `GOOGLE_GEMINI_BASE_URL` y demoras `Retry-After` acotadas por `max_delay`.

- **Normalización cross-provider de IDs de tool calls:** IDs sintéticos sin estado y resistentes a colisiones en `OpenAIEngine` (`#213`/`#230`) y `GeminiEngine` (`#231`/`#232`).

- **Validación en tiempo de ejecución con Pydantic:** Activada por defecto (`validate_args=True`, `ToolArgumentValidationError`, desactivable con `validate_args=False`), validación de uniones independiente del orden (`str | int`) y verificación estricta de números finitos (`allow_inf_nan=False`).
- **Mejoras de esquemas y tipado:** Los miembros de unión no representables lanzan `ToolSchemaError` al registrar la herramienta, `@tool` / `@agent.tool` proveen sobrecargas `@overload` precisas para tipado estático, las funciones comunes con parámetros `self`/`cls` los conservan en el esquema, `Tool.to_openai_parameters()` expone el JSON Schema normalizado y `json_codec` unificado lanza `JsonCodecError` ante metadatos de sesión no serializables.

### Sesiones, SQLite y Concurrencia
- **Ejecución SQLite serializada y no bloqueante:** Serialización por sesión en orden de llegada, descarga a hilos trabajadores para bases SQLite en archivo, rollbacks ante cancelación o timeout que aguardan escrituras SQLite en curso antes de restaurar estado, protección contra reentrada (`ReentrantTurnError`) y guardas `SessionDeletedError`.
- **Aislamiento y seguridad de hilos en memoria:** Deduplicación thread-safe en `SessionStore` (`record_processed_message()` / `is_message_processed()`) y aislamiento por copia profunda de metadatos en sesiones en memoria.

### Integraciones Telegram y WhatsApp
- **`TelegramChannel`:** Soporte para `concurrent_updates`, `/reset` seguro por sesión coordinado con `Runner.reset_session_async()` y reintentos acotados ante flood-control `RetryAfter` (`max_retry_after_seconds=60.0`) sin duplicar fragmentos enviados ni agregar `fallback_message` tras entrega parcial.

### Seguridad
- **Redacción de credenciales y sanitización de errores (desde `0.4.0rc3`):** Capa compartida de redacción de credenciales en `OpenAIEngine`, `AnthropicEngine`, `GeminiEngine` y logs salientes de `WhatsAppChannel` (enmascarando claves API, tokens y credenciales en URLs en texto plano, escapadas en JSON y en percent-encoding), excepciones `ProviderError` sanitizadas sin encadenar detalles internos de `httpx` ni `json.JSONDecodeError`, validación previa de credenciales en cabeceras HTTP, bloqueo de redirecciones con credenciales y mensajes/tracebacks acotados y redactados en `ToolArgumentValidationError`.

### Correcciones Importantes
- **Prevención de colisiones de IDs sintéticos de tool calls entre turnos en `GeminiEngine`** ([#231](https://github.com/GustavoBaranda/chatflow-agent/issues/231), [#232](https://github.com/GustavoBaranda/chatflow-agent/pull/232)): cuando Gemini omite `functionCall.id` o devuelve `None`, `""` o solo espacios, `GeminiEngine` genera ahora un ID de respaldo único sin estado con prefijo propio de Gemini (`cf_gemini_<24 hex>`, 34 caracteres, compatible con OpenAI y Anthropic) en lugar de reutilizar índices por respuesta (`call_{name}_{part_idx}`). Al reenviar historial a Gemini, `GeminiEngine` omite tanto el formato nuevo (`cf_gemini_<24 hex>`) como el legado (`call_{name}_{part_idx}`), conservando byte a byte los IDs reales del proveedor y los IDs de OpenAI y Anthropic.
- **Prevención de colisiones de IDs sintéticos de tool calls entre turnos en `OpenAIEngine`** ([#213](https://github.com/GustavoBaranda/chatflow-agent/issues/213), [#230](https://github.com/GustavoBaranda/chatflow-agent/pull/230)): cuando un proveedor compatible con OpenAI omite `tool_call.id` o devuelve `None`, `""` o solo espacios, `OpenAIEngine` genera ahora un ID de respaldo único sin estado (`call_<24 hex>`, 29 caracteres, compatible con OpenAI, Anthropic y Gemini) en lugar de reutilizar índices por respuesta (`call_0`, `call_1`). Los IDs no vacíos provistos por el proveedor se conservan sin cambios byte a byte.

### Cambios Incompatibles desde `0.3.x`
Para las instrucciones completas de actualización y ejemplos de código, consultá la [Guía de Migración a 0.4.0](docs/es/MIGRATION_0.4.md). Los cuatro cambios incompatibles confirmados entre `v0.3.4` y `0.4.0` son:
1. **Eliminación de `google-genai` y fin del soporte Vertex AI / ADC:** Las dependencias del núcleo son ahora únicamente `pydantic>=2.6.0` y `httpx>=0.27.0,<1.0`; `GeminiEngine` invoca directamente la API REST de Gemini Developer (`v1beta`) sobre `httpx` y requiere una API key explícita de Gemini en lugar de recurrir a Google Cloud Vertex AI / Application Default Credentials (ADC).
2. **Eliminación de `GeminiEngine.client`:** Se eliminó el atributo `GeminiEngine.client` (anteriormente un cliente de `google-genai`); en su lugar utilizá `http_client: httpx.AsyncClient | None = None` o un stub de `BaseEngine`.
3. **Rechazo de nombres duplicados de `Agent`:** Los grafos multi-agente que registren instancias distintas de `Agent` con el mismo `name` ahora lanzan error en lugar de sobrescribirse silenciosamente.
4. **Eliminación de `dedup_ttl_hours` en `WhatsAppChannel` y parámetros keyword-only:** Se eliminó el parámetro sin uso `dedup_ttl_hours` de `WhatsAppChannel` (el TTL de deduplicación se configura en el `SessionStore` / `SQLiteSessionStore` adjunto) y `max_body_size`, `enable_docs` y `queue_timeout_seconds` pasaron a ser solo por palabra clave.

### Cambios de Comportamiento Notables
- **Validación en tiempo de ejecución de argumentos de tools activada por defecto:** Los argumentos provistos por el modelo se validan y coaccionan con Pydantic (`ToolArgumentValidationError`, subclase de `ToolExecutionError`) antes de ejecutar la herramienta (`validate_args=True` por defecto; desactivable con `validate_args=False`).
- **Guarda estricta de event loop en `Runner.run()`:** Invocar `Runner.run()` dentro de un event loop ya activo lanza `RuntimeError`; utilizá `await runner.run_async(...)` en contextos asíncronos.

### Limitaciones Conocidas
- **IDs históricos persistidos en SQLite:** Los nuevos IDs sintéticos generados en `0.4.0` son únicos entre turnos, pero las sesiones SQLite creadas antes de `0.4.0` se conservan intactas en disco por compatibilidad hacia atrás. En consecuencia, los IDs sintéticos legados duplicados (`call_0`, `call_{name}_{part_idx}` o `""`) que ya existan en sesiones SQLite históricas todavía pueden propagarse a Anthropic y OpenAI durante handoffs entre proveedores.
- **Coordinación SQLite de nodo único:** `SQLiteSessionStore` aplica a un único proceso/nodo; los despliegues multi-nodo requieren un `BaseSessionStore` externo provisto por la aplicación.
- **Confirmación *at-most-once* en WhatsApp:** Registrar el `wamid` antes del despacho en segundo plano evita procesamientos duplicados con la contrapartida deliberada de perder un turno en vuelo si el proceso cae inmediatamente tras confirmar el webhook a Meta.

La deduplicación de estos mensajes pasa a ser determinista ante cambios en el orden de las claves y reinicios del proceso, manteniendo sin cambios los identificadores reales de WhatsApp y el comportamiento del formato genérico de webhook.
- **Reintentos ante Flood-Control y Envío Protegido de Fallback en Telegram** ([#175](https://github.com/GustavoBaranda/chatflow-agent/issues/175)): `TelegramChannel` ahora captura `telegram.error.RetryAfter` al enviar fragmentos de respuesta, espera de forma asíncrona la demora indicada por Telegram (acotada a una duración finita no negativa) y reintenta únicamente el fragmento pendiente hasta 3 veces en lugar de saltar de inmediato al manejador de errores. Los fragmentos ya enviados nunca se duplican, y si un envío falla después de haber entregado contenido parcial (o tras agotarse los reintentos por flood-control), el canal detiene el envío sin agregar un `fallback_message` contradictorio. El envío de `fallback_message` ante errores previos a la entrega ahora está protegido para que una segunda excepción de envío se registre en el log en lugar de propagarse sin manejar desde `_handle_message`, y los logs de error de los handlers registran únicamente el nombre de la clase de excepción (`type(err).__name__`) en vez del mensaje bruto de la excepción.
- **Validación de la Configuración de Envío y Tamaño de Payload de WhatsApp** ([#198](https://github.com/GustavoBaranda/chatflow-agent/pull/198) por [@MbappeWU](https://github.com/MbappeWU), [#175](https://github.com/GustavoBaranda/chatflow-agent/issues/175)): `WhatsAppChannel` ahora rechaza configuraciones inválidas de reintentos de envío y tamaño del payload del webhook al construir el canal mediante `ConfigurationError` (subclase de `ValueError`). `max_outbound_retries` debe ser un entero entre 0 y 10; `outbound_base_delay` y `outbound_max_delay` deben ser números reales finitos mayores o iguales a cero; y `max_body_size` debe ser un entero positivo. Los booleanos se rechazan en los cuatro parámetros. Los valores por defecto, cero reintentos, delays de cero y un delay máximo menor que el delay base siguen siendo válidos. Las configuraciones que dependían de valores inválidos, incluidos tamaños de payload float como `2e6`, ahora fallan inmediatamente en lugar de romper el backoff o los límites de payload en runtime.
- **La Documentación Coincide con la Implementación** ([#172](https://github.com/GustavoBaranda/chatflow-agent/issues/172)):
  - la Guía de Arquitectura ya no afirma que `GeminiEngine` fusiona turnos consecutivos ni que preserva `thoughtSignature`, y su árbol de excepciones ahora incluye `ToolArgumentValidationError` y `JsonCodecError`;
  - la Guía de Migración indica la firma real `replacement_tool_call_id(call_id)` y ya no afirma que `Agent.provider` vale `"gemini"` por defecto (vale `None`);
  - los README limitan WAL a los almacenes SQLite en archivo (los almacenes `":memory:"` no usan WAL) y listan los prefijos de modelo `text-embedding-` y `dall-e`;
  - `SECURITY.md` incluye las versiones preliminares de `0.4.0` como destinadas a pruebas y evaluación, sin backports ni tiempos de respuesta garantizados (`0.3.4` sigue siendo la versión estable soportada), y tiene la misma nota de cierre en inglés y en español;
  - ambos README muestran el logo del proyecto para los temas claro y oscuro de GitHub, reconocen a los colaboradores verificados `dannyward630` e `IENVYshanks` y corrigen los enlaces internos a las secciones de contribución y apoyo.

  Las versiones en inglés y en español se actualizaron juntas.
- **El Hook `on_24h_window_expired` de WhatsApp se Ejecuta con Cualquier Invocable Asíncrono** ([#196](https://github.com/GustavoBaranda/chatflow-agent/pull/196) por [@GustavoBaranda](https://github.com/GustavoBaranda), [#175](https://github.com/GustavoBaranda/chatflow-agent/issues/175)): el hook se clasificaba con `asyncio.iscoroutinefunction`, que no reconoce objetos con `async __call__`, envoltorios `functools.partial` de ellos ni funciones comunes que devuelven una corrutina. Con esos hooks la corrutina se creaba pero nunca se esperaba, por lo que el hook nunca se ejecutaba, sin ningún error, y Python emitía `RuntimeWarning: coroutine ... was never awaited`. Ahora el canal invoca el hook y espera su resultado siempre que sea awaitable, lo que además elimina el uso de `asyncio.iscoroutinefunction`, deprecado en Python 3.14. Los hooks `async def` y los síncronos se comportan como antes: los síncronos se siguen ejecutando en línea sobre el event loop y no deben bloquear, y las excepciones de cualquier hook se siguen registrando en el log sin interrumpir la entrega saliente.
- **Encabezados `Retry-After` Inválidos Recurren a Backoff Exponencial** ([#194](https://github.com/GustavoBaranda/chatflow-agent/pull/194) por [@MbappeWU](https://github.com/MbappeWU), [#175](https://github.com/GustavoBaranda/chatflow-agent/issues/175)): los valores `Retry-After` negativos o no finitos en los reintentos salientes de `WhatsAppChannel`, `OpenAIEngine` y `AnthropicEngine` ahora se tratan como inválidos y recurren al backoff exponencial en lugar de reintentar de inmediato, igualando el comportamiento de `GeminiEngine`.
- **Enmascarado del Teléfono Remitente en Respuestas JSON del Webhook de WhatsApp** ([#192](https://github.com/GustavoBaranda/chatflow-agent/pull/192) por [@MbappeWU](https://github.com/MbappeWU), [#175](https://github.com/GustavoBaranda/chatflow-agent/issues/175)): `WhatsAppChannel` ahora enmascara el campo `sender` en las respuestas JSON del webhook mediante `_mask_phone()`, igualando la redacción de logs para no exponer números telefónicos reales a proxies inversos ni herramientas de APM.
- **Parámetros `self`/`cls` en Funciones Comunes Conservados en Esquemas de Herramientas** ([#191](https://github.com/GustavoBaranda/chatflow-agent/pull/191) por [@MbappeWU](https://github.com/MbappeWU), [#176](https://github.com/GustavoBaranda/chatflow-agent/issues/176)): `Tool` ya no elimina parámetros llamados `self` o `cls` de los esquemas ni de los validadores mediante heurísticas de GC/métodos; `Tool.execute()`, `execute_async()` y `__call__()` declaran `self` como posicional puro para que argumentos por palabra clave llamados `self` lleguen a la función envuelta. Los métodos de instancia y de clase deben registrarse como métodos enlazados.
- **Codificación JSON Consistente para Resultados de Herramientas y Metadatos de Sesión** ([#188](https://github.com/GustavoBaranda/chatflow-agent/pull/188) por [@MbappeWU](https://github.com/MbappeWU), [#167](https://github.com/GustavoBaranda/chatflow-agent/issues/167)): se unificó la serialización JSON entre motores y almacenes de sesión mediante `json_codec`, codificando `datetime`/`date`/`time` como ISO-8601. La serialización de metadatos de sesión falla tempranamente con `JsonCodecError` ante objetos no soportados, mientras que la codificación en cable de resultados de herramientas conserva la coerción a texto para valores hoja no JSON.
- **Detención de Fragmentos Salientes de WhatsApp ante Fallos y Protección contra Respuestas Vacías** ([#180](https://github.com/GustavoBaranda/chatflow-agent/pull/180) por [@MbappeWU](https://github.com/MbappeWU), [#169](https://github.com/GustavoBaranda/chatflow-agent/issues/169)): `WhatsAppChannel` ahora detiene el envío de los fragmentos restantes apenas falla uno en lugar de continuar la entrega; las respuestas vacías o solo con espacios envían `fallback_message` tanto en `WhatsAppChannel` como en `TelegramChannel`; y `WhatsAppChannel` registra una advertencia al construirse si faltan `access_token` o `phone_number_id`.
- **Respeto de `Agent(api_key=...)` en el Fallback Predeterminado de Gemini** ([#179](https://github.com/GustavoBaranda/chatflow-agent/pull/179) por [@GustavoBaranda](https://github.com/GustavoBaranda), [#163](https://github.com/GustavoBaranda/chatflow-agent/issues/163)): cuando un `Agent` especifica `api_key=...` sin `engine`, `provider` ni `base_url` explícitos y `resolve_engine()` recurre a un `GeminiEngine` base, ahora devuelve una copia configurada con la clave del agente preservando el resto de sus ajustes.
- **Tipos Estáticos Precisos para `tool()` y `Agent.tool()`** ([#195](https://github.com/GustavoBaranda/chatflow-agent/pull/195) por [@GustavoBaranda](https://github.com/GustavoBaranda), [#176](https://github.com/GustavoBaranda/chatflow-agent/issues/176)): ambos decoradores estaban anotados con retorno `Any`, por lo que los verificadores de tipos perdían el tipo de cada herramienta decorada y `mypy --strict` informaba "Untyped decorator makes function … untyped" en las formas con argumentos. Ahora, firmas `@overload` declaran lo que devuelven en tiempo de ejecución: `@tool` / `@agent.tool` devuelven un `Tool`, y las formas con argumentos (`@tool()`, `@tool("name")`, `@tool(name=...)`, `@agent.tool(...)`) devuelven un decorador que produce un `Tool`. El comportamiento en tiempo de ejecución no cambia. Para usuarios de mypy: los accesos a atributos inválidos sobre una herramienta decorada ahora se informan, y los comentarios `# type: ignore[untyped-decorator]` existentes pueden quedar sin uso, lo que `--strict` informa mediante `warn_unused_ignores`. El CI verifica estos tipos con `mypy --strict tests/type_checks/decorators.py`.
- **Prevención de Fallbacks Silenciosos de Proveedor y Endpoint** ([#183](https://github.com/GustavoBaranda/chatflow-agent/pull/183) por [@GustavoBaranda](https://github.com/GustavoBaranda), [#166](https://github.com/GustavoBaranda/chatflow-agent/issues/166)): la configuración explícita de `provider` en un `Agent` ahora se valida estrictamente contra el conjunto de proveedores soportados (`gemini`, `google`, `openai`, `grok`, `xai`, `deepseek`, `groq`, `ollama`, `gemma`, `anthropic`, `claude`); proveedores no soportados (como `"mistral"`) levantan `ConfigurationError` inmediatamente en lugar de derivar silenciosamente a heurísticas de prefijo de modelo y endpoints locales no intencionados. Combinar `provider="gemini"` o `"google"` con `base_url` levanta `ConfigurationError` en vez de ignorar el endpoint (los endpoints personalizados de Gemini deben usar la variable de entorno `GOOGLE_GEMINI_BASE_URL`). Endpoints remotos personalizados sin `api_key` levantan `ConfigurationError` tempranamente al inicializar el `Runner` en lugar de fallar a mitad del turno con un `ValueError` genérico. `OpenAIEngine(provider=...)` con un proveedor no reconocido sin `base_url` explícito levanta `ConfigurationError` en lugar de degradar a OpenAI. Prefijos de modelos no reconocidos sin un proveedor explícito conservan su fallback documentado a Gemini.
- **Los Argumentos de Unión Ignoran el Orden de los Miembros** ([#178](https://github.com/GustavoBaranda/chatflow-agent/pull/178) por [@bfs2021](https://github.com/bfs2021), [#168](https://github.com/GustavoBaranda/chatflow-agent/issues/168)): la validación de argumentos en tiempo de ejecución ya no convierte un entero en cadena solo porque `str` se escribió primero en `str | int`. La unión saneada prueba antes los miembros que no coercionan, por lo que un valor que ya coincide exactamente con un miembro se entrega sin cambios, y la coerción de número a cadena sigue aplicándose cuando ningún otro miembro acepta el valor. Cambia el valor entregado para herramientas anotadas `str | int` que antes recibían `"5"`: ahora reciben `5`.
- **Aislamiento de Metadatos de Sesiones en Memoria** ([#177](https://github.com/GustavoBaranda/chatflow-agent/pull/177) por [@dannyward630](https://github.com/dannyward630), [#162](https://github.com/GustavoBaranda/chatflow-agent/issues/162)): las sesiones en memoria realizan una copia profunda de los metadatos al crearse. Las sesiones inicializadas con el mismo diccionario ya no comparten valores anidados entre sí ni con quien lo proporcionó; las actualizaciones del turno, los handoffs y el rollback de turnos fallidos conservan ese aislamiento. La serialización de SQLite no cambia. Quien dependía de modificar el diccionario original para actualizar una sesión activa debe usar `SessionContext.update_metadata()`.
- **Deduplicación de `SessionStore` en Memoria Ahora es Thread-Safe** ([#147](https://github.com/GustavoBaranda/chatflow-agent/pull/147) por [@GustavoBaranda](https://github.com/GustavoBaranda)): `SessionStore.record_processed_message()` e `is_message_processed()` quedan protegidas por un candado interno, de modo que hilos concurrentes que comparten un mismo store en memoria ya no pueden aceptar dos veces el mismo id de mensaje. La semántica de expiración, purga y capacidad no cambia, igual que el comportamiento de `SQLiteSessionStore`, `Runner` y los canales. (REC-01 de la auditoría de estabilización de `v0.4.0rc1`.)
- **Sanitización de Errores y Tracebacks en Validación de Argumentos** ([#160](https://github.com/GustavoBaranda/chatflow-agent/pull/160) por [@GustavoBaranda](https://github.com/GustavoBaranda)): `ToolArgumentValidationError` sanitiza los errores de validación integrados impidiendo la exposición de valores de entrada sensibles, credenciales, claves no confiables provistas por el modelo o rutas anidadas en `str(exc)`, `repr(exc)`, `exc.args` y tracebacks de excepción (`__cause__` y `__context__` se suprimen estrictamente). La cantidad de errores (máximo 3) y la longitud total del mensaje (máximo 300 caracteres) están estrictamente acotadas. Excepciones lanzadas explícitamente por validadores personalizados definidos por el usuario no garantizan la redacción si incluyen datos de entrada en su propio código.

### ⚠ CAMBIOS CON RUPTURA DE COMPATIBILIDAD (BREAKING CHANGES)
1. **`GeminiEngine` Utiliza la API REST de Gemini vía `httpx`; `google-genai` Eliminado y Vertex AI Ya No Está Soportado** ([#130](https://github.com/GustavoBaranda/chatflow-agent/pull/130) por [@Gokulnaath07](https://github.com/Gokulnaath07), [#116](https://github.com/GustavoBaranda/chatflow-agent/issues/116)): `GeminiEngine` ahora llama a la Gemini Developer API (Google AI Studio) mediante REST con una clave API, y `google-genai` ya no es una dependencia de chatflow-agent (las dependencias centrales del runtime son `pydantic` y `httpx`). Application Default Credentials y las variables `GOOGLE_GENAI_USE_VERTEXAI`, `GOOGLE_CLOUD_PROJECT` y `GOOGLE_CLOUD_LOCATION`, que `google-genai` podía utilizar, son ignoradas; dichas configuraciones ahora fallan con `ProviderError("Gemini API client is not configured. ...")`. Utilizá una clave API de Gemini (`GEMINI_API_KEY`, `GOOGLE_API_KEY` o `api_key=...`), o proporcioná tu propio `BaseEngine` mediante `Runner(engine=...)`.
2. **`GeminiEngine.client` Eliminado** ([#130](https://github.com/GustavoBaranda/chatflow-agent/pull/130) por [@Gokulnaath07](https://github.com/Gokulnaath07), [#116](https://github.com/GustavoBaranda/chatflow-agent/issues/116)): el atributo contenía el `google.genai.Client` (o `None` si no podía crearse) y ya no existe. Leerlo levanta `AttributeError`; asignarlo (por ejemplo, un cliente simulado en un test) no genera excepción pero no tiene ningún efecto, enviando las peticiones a la API real. Migración:
   - **Llamadas directas al SDK** (por ejemplo, listar modelos o subir archivos): instalá `google-genai` por tu cuenta y creá tu propio `genai.Client`.
   - **Mocking de Gemini en tests o personalización de HTTP** (proxies, TLS, transportes): pasá un `httpx.AsyncClient` con `GeminiEngine(http_client=...)`, por ejemplo `httpx.AsyncClient(transport=httpx.MockTransport(handler))`, y utilizá el motor a través de `Runner(engine=...)` (proporcioná la clave a `GeminiEngine(api_key=...)` o definí `GEMINI_API_KEY`; en tal caso `Runner(api_key=...)` no se utiliza). Las respuestas siguen la API REST de Gemini (`generateContent`), no los objetos del SDK. El cliente pertenece a quien lo invoca: chatflow-agent nunca lo cierra y debe utilizarse en un único bucle de eventos, por lo que no es apto para `Runner.run()` ni `CLIChannel`, que inician un bucle nuevo en cada llamada.
3. **Se Rechazan Instancias Distintas de `Agent` con el Mismo Nombre** ([#128](https://github.com/GustavoBaranda/chatflow-agent/pull/128) por [@MbappeWU](https://github.com/MbappeWU), coautoría con [@GustavoBaranda](https://github.com/GustavoBaranda), [#123](https://github.com/GustavoBaranda/chatflow-agent/issues/123)): construir un `Runner` cuyo grafo de handoffs contenga dos instancias distintas de `Agent` con el mismo `name` ahora levanta `ValueError`; anteriormente la segunda instancia se ignoraba silenciosamente y sus handoffs se redirigían a la primera. La misma verificación aplica a `add_handoff()` tras la inicialización y a `register_agent()`; un cambio rechazado deja el registro sin alterar. Reutilizar una misma instancia de `Agent` en varias ramas o en ciclos sigue funcionando normalmente. Asigná a cada agente distinto un nombre único.

### Modificado
- **Timeouts de WhatsApp: Espera y Turno se Limitan por Separado** ([#93](https://github.com/GustavoBaranda/chatflow-agent/pull/93) por [@dbdefault](https://github.com/dbdefault), [#91](https://github.com/GustavoBaranda/chatflow-agent/issues/91); [#131](https://github.com/GustavoBaranda/chatflow-agent/pull/131) por [@GustavoBaranda](https://github.com/GustavoBaranda)): el valor por defecto de `llm_timeout_seconds` aumentó de 30 a 120 segundos, y ahora acota únicamente la duración del turno desde que adquiere la sesión; la espera por la sesión está acotada por `queue_timeout_seconds`. Una respuesta puede tardar hasta `queue_timeout_seconds + llm_timeout_seconds` (240 s con los valores por defecto). Un mensaje cuya espera vence recibe `fallback_message` y su turno nunca se ejecuta. Un método `dispatch_async()` personalizado que no invoque `Runner.run_async()` queda acotado por dicha suma más un segundo. `None` e `inf` siguen sin aplicar límite de turno, y valores menores o iguales a cero hacen vencer cada turno de inmediato; `nan` ahora no impone límite (anteriormente causaba vencimientos inmediatos o detenía el bucle en Python 3.13). Valores menores o iguales a cero o `nan` emiten una advertencia en el log.
- **Logs de Timeout en WhatsApp** ([#131](https://github.com/GustavoBaranda/chatflow-agent/pull/131) por [@GustavoBaranda](https://github.com/GustavoBaranda)): el mensaje único de error `LLM dispatch timed out ...` se reemplaza por `Session busy ...` (límite de cola), `Turn timed out ...` (límite de turno), `Dispatch backstop expired ...` (un `dispatch_async()` que nunca invocó `Runner.run_async()`) y `TimeoutError raised while dispatching ...` (un `TimeoutError` emitido por el proveedor u otro componente). Es necesario actualizar alertas que filtren por el texto previo.
- **Llamadas a Turnos desde un Turno Activo Levantan Excepción** ([#120](https://github.com/GustavoBaranda/chatflow-agent/pull/120) por [@GustavoBaranda](https://github.com/GustavoBaranda), [#31](https://github.com/GustavoBaranda/chatflow-agent/issues/31)): invocar `Runner.run_async()` o `Runner.run()` para una sesión desde código ejecutado por un turno en curso de esa misma sesión (una herramienta, o cualquier tarea o hilo que inicie: `create_task`, `gather`, `wait_for`, `TaskGroup`, `asyncio.to_thread`) ahora levanta `ReentrantTurnError` inmediatamente. Con anterioridad, dichas llamadas se bloqueaban indefinidamente (almacenamiento en memoria) o se ejecutaban concurrentemente sin serializar junto al turno externo (SQLite). Utilizá `Runner.spawn_turn()` para turnos de seguimiento. Aplica a cualquier implementación de almacenamiento de sesión, incluyendo stores personalizados.
- **Turnos en SQLite se Procesan Secuencialmente por Orden de Llegada** ([#120](https://github.com/GustavoBaranda/chatflow-agent/pull/120), [#133](https://github.com/GustavoBaranda/chatflow-agent/pull/133) por [@GustavoBaranda](https://github.com/GustavoBaranda)): peticiones concurrentes sobre un mismo `session_id` en SQLite se ejecutan de manera estrictamente secuencial, esperando la solicitud encolada al turno previo. En stores respaldados por archivo, el turno adquiere el candado antes de cargar el estado, garantizando el orden de inicio. Un turno que se encuentra ejecutándose al momento de eliminarse su sesión falla indefectiblemente con `SessionDeletedError`.
- **Turnos Cancelados Aguardan la Finalización de su Escritura SQLite en Curso** ([#133](https://github.com/GustavoBaranda/chatflow-agent/pull/133) por [@GustavoBaranda](https://github.com/GustavoBaranda)): cancelar un turno o alcanzar su `turn_timeout` mientras una escritura SQLite está en ejecución espera a que dicha operación concluya, luego ejecuta el rollback del turno y recién entonces propaga la excepción; la sesión permanece bloqueada durante dicho intervalo. La detección del timeout ocurre puntualmente, pero su `TimeoutError` (y la respuesta de fallback en WhatsApp) pueden emitirse posteriormente: hasta el lapso de `busy_timeout` de SQLite (10 s; algo mayor en Windows) por escritura pendiente mientras otro proceso retiene la base. Una escritura que no haya iniciado aún es cancelada de inmediato. Si el propio rollback falla, se levanta y registra su error (`Rolling back the failed turn of session ... failed`); el turno nunca se reporta como revertido exitosamente.
- **Tiempos de Reintento en `GeminiEngine` Acotados por `max_delay`** ([#130](https://github.com/GustavoBaranda/chatflow-agent/pull/130) por [@Gokulnaath07](https://github.com/Gokulnaath07), [#116](https://github.com/GustavoBaranda/chatflow-agent/issues/116)): ante respuestas 429, 500, 502, 503 o 504, el encabezado `Retry-After` (segundos o fecha HTTP en cualquiera de los tres formatos estándar) reemplaza al backoff exponencial, pero la espera nunca excede `max_delay` (10 s por defecto). Valores malformados (por ejemplo `soon`, `-5`, `nan` o fechas inválidas) se ignoran, aplicándose el backoff exponencial habitual.
- **Tipos de Parámetro No Soportados en Herramientas Fallan al Registrarse** ([#118](https://github.com/GustavoBaranda/chatflow-agent/pull/118) por [@rahul05ranjan](https://github.com/rahul05ranjan), [#115](https://github.com/GustavoBaranda/chatflow-agent/issues/115)): un parámetro de herramienta con una anotación de unión que contenga un miembro sin mapeo concreto a JSON Schema levanta `ToolSchemaError` al momento de inicializar la herramienta, en vez de registrarse silenciosamente como tipo `string`; las anotaciones fuera de uniones que no puedan expresarse conservan el fallback previo `STRING` (Gemini) / `string` (OpenAI).
- **Validaciones de Entrada Más Estrictas:** `Runner.run()` invocado dentro de un bucle de eventos activo levanta `RuntimeError` indicando utilizar `await runner.run_async(...)` ([#57](https://github.com/GustavoBaranda/chatflow-agent/pull/57) por [@ompatil1906](https://github.com/ompatil1906), [#56](https://github.com/GustavoBaranda/chatflow-agent/issues/56)); nombres de `Agent` vacíos o compuestos únicamente por espacios levantan `ValueError` ([#86](https://github.com/GustavoBaranda/chatflow-agent/pull/86) por [@jay23606](https://github.com/jay23606), [#84](https://github.com/GustavoBaranda/chatflow-agent/issues/84)); valores no positivos de `max_turns` / `default_max_turns` en contextos y almacenes levantan `ValueError` ([#63](https://github.com/GustavoBaranda/chatflow-agent/pull/63) por [@sarantez](https://github.com/sarantez), [#59](https://github.com/GustavoBaranda/chatflow-agent/issues/59)); `split_message()` con `max_len <= 0` levanta `ValueError` en lugar de ciclar indefinidamente ([#46](https://github.com/GustavoBaranda/chatflow-agent/pull/46) por [@krishna2707](https://github.com/krishna2707), [#45](https://github.com/GustavoBaranda/chatflow-agent/issues/45)).
- **Código de Estado HTTP 413 en WhatsApp** ([#136](https://github.com/GustavoBaranda/chatflow-agent/pull/136) por [@GustavoBaranda](https://github.com/GustavoBaranda)): `WhatsAppChannel` ya no referencia la constante obsoleta `HTTP_413_REQUEST_ENTITY_TOO_LARGE` de Starlette; payloads con tamaño excesivo continúan rechazándose con código HTTP 413.

### Corregido
- **Herramientas Síncronas Solapadas tras Timeout de Turno** ([#142](https://github.com/GustavoBaranda/chatflow-agent/pull/142) por [@GustavoBaranda](https://github.com/GustavoBaranda)): cuando una herramienta síncrona (`def`) ejecutada mediante `asyncio.to_thread()` excede `turn_timeout`, su hilo de trabajo continúa ejecutándose en segundo plano debido a restricciones del runtime de hilos en Python. La barrera del candado de sesión ahora registra el ticket del trabajo síncrono activo y aguarda hasta `queue_timeout_seconds` antes de permitir que turnos subsiguientes en la misma sesión adquieran el candado. Si el hilo de trabajo intenta invocar un turno anidado en la misma sesión mientras drena, es rechazado inmediatamente con `ReentrantTurnError`.
- **Integridad de Sesiones SQLite ante Solicitudes Concurrentes** ([#120](https://github.com/GustavoBaranda/chatflow-agent/pull/120) por [@GustavoBaranda](https://github.com/GustavoBaranda), [#31](https://github.com/GustavoBaranda/chatflow-agent/issues/31)): turnos sobre un mismo `session_id` en `SQLiteSessionStore` comparten un candado por bucle de eventos; anteriormente cada solicitud obtenía un candado independiente y corrían en paralelo. Cada turno recarga el historial, agente activo y metadata confirmados tras obtener el candado. Un turno fallido o cancelado no elimina ni sobrescribe datos confirmados concurrentemente: revierte únicamente sus propias modificaciones mediante una única transacción `BEGIN IMMEDIATE` y emite una advertencia. El registro de candados utiliza referencias débiles (`WeakValueDictionary`) y segrega candados por bucle de eventos, manteniendo la compatibilidad con llamadas sucesivas a `Runner.run()`.
- **SQLite No Bloquea el Bucle de Eventos** ([#133](https://github.com/GustavoBaranda/chatflow-agent/pull/133) por [@GustavoBaranda](https://github.com/GustavoBaranda)): en almacenes `SQLiteSessionStore` basados en archivo, las operaciones de sesión del Runner, la deduplicación del webhook de WhatsApp y `/reset` en Telegram se delegan a un pool dedicado de hilos de trabajo propio del almacén (4 hilos, inicializados en el primer uso y cerrados vía `close()`). Latencias de disco o bloqueos por otros procesos ya no suspenden el bucle de eventos de la aplicación. Almacenes en memoria (`:memory:`), clases base `SessionStore`, subclases e implementaciones personalizadas continúan operando en el bucle principal.
- **Deduplicación Atómica de WhatsApp en SQLite** ([#120](https://github.com/GustavoBaranda/chatflow-agent/pull/120) por [@GustavoBaranda](https://github.com/GustavoBaranda)): `SQLiteSessionStore.record_processed_message()` verifica y almacena el identificador del mensaje en una única sentencia, impidiendo el procesamiento dual ante entregas concurrentes del mismo `wamid`. Requiere SQLite 3.24 o posterior.
- **Sesiones Eliminadas No Reciben Mensajes Huérfanos** ([#120](https://github.com/GustavoBaranda/chatflow-agent/pull/120) por [@GustavoBaranda](https://github.com/GustavoBaranda)): un turno en ejecución cuya sesión SQLite es borrada falla con `SessionDeletedError` en lugar de guardar respuestas desvinculadas. Un turno en espera de una sesión eliminada inicia una sesión nueva y vacía; los datos eliminados nunca se restauran.
- **Rollback Completo de Turnos Fallidos:** un turno fallido restaura mensajes podados durante el turno ([#34](https://github.com/GustavoBaranda/chatflow-agent/pull/34) por [@KeuqS](https://github.com/KeuqS), [#32](https://github.com/GustavoBaranda/chatflow-agent/issues/32)), el agente activo y la metadata ([#52](https://github.com/GustavoBaranda/chatflow-agent/pull/52) por [@aazminu](https://github.com/aazminu), [#51](https://github.com/GustavoBaranda/chatflow-agent/issues/51)), aplicándose igualmente ante cancelaciones ([#69](https://github.com/GustavoBaranda/chatflow-agent/pull/69) por [@Aaqibhafeezkhan](https://github.com/Aaqibhafeezkhan), [#60](https://github.com/GustavoBaranda/chatflow-agent/issues/60)).
- **Persistencia de Metadata de Sesión:** `Handoff.context_updates` se guarda al momento de ejecutarse la transferencia ([#41](https://github.com/GustavoBaranda/chatflow-agent/pull/41) por [@mikemikimike](https://github.com/mikemikimike), [#37](https://github.com/GustavoBaranda/chatflow-agent/issues/37)), y la metadata provista a `run_async()` se persiste en cada turno ([#95](https://github.com/GustavoBaranda/chatflow-agent/pull/95) por [@Erfouni](https://github.com/Erfouni), [#89](https://github.com/GustavoBaranda/chatflow-agent/issues/89)).
- **Handoffs:** las transferencias resuelven hacia el par declarado por el agente actual, evitando que especialistas homónimos en distintas ramas intercepten handoffs ajenos ([#128](https://github.com/GustavoBaranda/chatflow-agent/pull/128) por [@MbappeWU](https://github.com/MbappeWU), [#123](https://github.com/GustavoBaranda/chatflow-agent/issues/123)); handoffs registrados con `add_handoff()` con posterioridad a la creación del `Runner` son resueltos adecuadamente ([#112](https://github.com/GustavoBaranda/chatflow-agent/pull/112) por [@dbdefault](https://github.com/dbdefault), [#105](https://github.com/GustavoBaranda/chatflow-agent/issues/105)); se preservan las herramientas de usuario ante colisiones de nombre con herramientas de handoff ([#49](https://github.com/GustavoBaranda/chatflow-agent/pull/49) por [@jsdhwfmax](https://github.com/jsdhwfmax), [#48](https://github.com/GustavoBaranda/chatflow-agent/issues/48)); nombres de agente no-ASCII generan identificadores de herramientas de handoff unívocos ([#108](https://github.com/GustavoBaranda/chatflow-agent/pull/108) por [@dbdefault](https://github.com/dbdefault), [#104](https://github.com/GustavoBaranda/chatflow-agent/issues/104)); alcanzar `max_handoffs_per_turn` garantiza el retorno de un resultado para cada llamada a herramienta ([#50](https://github.com/GustavoBaranda/chatflow-agent/pull/50) por [@jsdhwfmax](https://github.com/jsdhwfmax), [#27](https://github.com/GustavoBaranda/chatflow-agent/issues/27)).

### Problemas Conocidos
- **Alcance de la Concurrencia:** No se provee serialización entre instancias de almacenamiento sobre el mismo archivo, entre procesos independientes ni entre hilos con bucles de eventos desacoplados.
- **Turnos Anidados Externos a las Tareas del Turno:** una herramienta que aguarde la finalización de trabajo delegado en una tarea externa (por ejemplo, un worker previo) puede bloquearse si dicho trabajo invoca un turno para la misma sesión. Esperar con `await` una tarea devuelta por `spawn_turn()` dentro del mismo turno que la creó genera igualmente interbloqueo.
- **Contención en SQLite Retrasa Peticiones que Requieren la Base:** una operación SQLite iniciada no puede interrumpirse. Mientras otro proceso retiene la base, el webhook de WhatsApp confirmará únicamente tras su escritura de deduplicación (preservando la semántica at-most-once), esperando dicha respuesta HTTP; si la contención supera `busy_timeout`, el webhook responderá HTTP 500 y el reintento de Meta será procesado al no haberse registrado el mensaje. El apagado del servicio puede aguardar escrituras en curso. No se soporta la concurrencia de múltiples procesos sobre un mismo archivo SQLite: ejecutar SQLite fuera del bucle de eventos no coordina procesos externos.
- **Reset y Delete Durante un Turno:** `clear_history()` y `delete()` no coordinan transacciones con turnos en curso más allá de las garantías de rollback y excepciones `SessionDeletedError` documentadas previamente (seguimiento por separado).

- **Recomendación de Rate Limiting con Reverse Proxy (SEC-06):** Se añadió documentación de despliegue en producción recomendando ubicar Uvicorn detrás de un reverse proxy (como Nginx con `limit_req_zone` o Cloudflare Rate Limiting) para proteger los endpoints `/webhook` y `/health` contra ataques de inundación y agotamiento de CPU por peticiones no autenticadas, evitando rate limiting a nivel aplicación que pudiera descartar ráfagas legítimas de webhooks de Meta (Issue #10).

Cuando se proporciona un `base_url` personalizado (que no coincide con los presets oficiales ni con localhost/127.0.0.1) sin una `api_key` explícita, se levanta un `ValueError`, exigiendo una `api_key` explícita (o `api_key=""` si no requiere autenticación) (Issue #11).
- **División de Mensajes Salientes en Telegram (SEC-08):** `TelegramChannel` ahora divide las respuestas salientes que superan el límite de 4.096 caracteres de Telegram en fragmentos progresivos usando `split_message()`, previniendo fallos sistemáticos de entrega y respuestas de error en respuestas extensas de LLM. `split_message()` ahora reside en `chatflow_agent.channels.base` y se reexporta desde `whatsapp` para retrocompatibilidad (Issue #12).

## [0.3.1] - 2026-09-25

### Seguridad
- **Límite de Tamaño en Request Body del Webhook de WhatsApp (SEC-01):** Se corrigió una vulnerabilidad donde las peticiones entrantes `POST /webhook` no validaban el tamaño del payload antes de cargarlo en memoria, permitiendo ataques de Denegación de Servicio por agotamiento de memoria (DoS / OOM). Ahora se valida el encabezado `Content-Length` antes de leer el cuerpo, aplicando un límite configurable (por defecto 1 MB mediante `DEFAULT_MAX_BODY_SIZE`) y rechazando payloads excesivos con HTTP 413, encabezados ausentes con HTTP 411 y encabezados malformados con HTTP 400.

## [0.3.0] - 2026-09-21

### Seguridad
- **Verificación Obligatoria de Firma en Webhook de WhatsApp (SEC-01):** Se corrigió una vulnerabilidad en `WhatsAppChannel` donde las peticiones POST `/webhook` entrantes se procesaban sin validar la cabecera HMAC `X-Hub-Signature-256` de Meta, permitiendo a un atacante enviar mensajes falsificados suplantando números de usuario. `WhatsAppChannel` ahora aplica una política estricta *fail-closed*: exige `app_secret` por defecto, valida la firma con `hmac.compare_digest` en tiempo constante y rechaza cualquier petición sin firma válida con HTTP 403.
- **Mitigación de Ataques de Temporización (SEC-02):** La verificación del handshake GET `/webhook` utiliza `hmac.compare_digest` en tiempo constante para validar el token.
- **Enmascaramiento de Credenciales en Logs:** Tokens, secretos de aplicación y números telefónicos se enmascaran automáticamente en toda la salida de depuración y logs.
- **Plantillas con Validación Estricta (Fail-Closed):** Los ejemplos (`whatsapp_service.py` y `whatsapp_persistent_bot.py`) lanzan `RuntimeError` si falta `WHATSAPP_APP_SECRET` en vez de usar un secreto de desarrollo inseguro por defecto.

### ⚠ CAMBIOS CON RUPTURA DE COMPATIBILIDAD (BREAKING CHANGES)
1. **`WhatsAppChannel` exige `app_secret` por defecto (SEC-01):** Si se omite `app_secret`, se lanza `ValueError` al arrancar el servidor a menos que se configure explícitamente `verify_signature=False` (solo para pruebas locales).
2. **Cambio en el cuerpo de respuesta del Webhook (BUS-01):** El POST `/webhook` ahora responde `{"status":"success","sender":"...","messages_queued": N}`. La inferencia y el envío saliente se procesan asíncronamente en segundo plano.
3. **`max_turns` ahora cuenta turnos completos de usuario (DATA-01):** `max_turns` mide ciclos conversacionales completos (mensaje del usuario + respuestas del modelo + herramientas asociadas) en vez de objetos de mensaje individuales.

### Agregado / Corregido
- **Despacho Asíncrono de Webhooks (BUS-01):** Responde HTTP 200 a Meta inmediatamente, evitando tormentas de reintentos por latencia del LLM.
- **Deduplicación At-Most-Once (ARCH-01):** Registro atómico por `wamid` en SQLite con TTL de 8 días (`DEFAULT_DEDUP_TTL_HOURS = 192`) que descarta reintentos duplicados de Meta.
- **Extracción de Lotes Multi-Mensaje:** Procesamiento y despacho independiente para webhooks que contienen múltiples mensajes simultáneos.
- **Reintentos Salientes Selectivos con Jitter:** Limitados estrictamente a errores de conexión de red y HTTP 429 con jitter, respetando el encabezado `Retry-After`.
- **Manejo de Ventana de 24h de Meta:** Detección del código de error `131047`, ejecución protegida con try/except del hook `on_24h_window_expired` y log con teléfono enmascarado.
- **División Automática de Mensajes Salientes:** Fragmentación automática de mensajes que exceden el límite de 4.096 caracteres de Meta respetando párrafos y oraciones.
- **Rollback ante Fallas a Mitad de Turno:** Reversión automática del historial conversacional al último turno consistente en memoria y SQLite ante fallas del LLM, garantizando la entrega del mensaje de fallback.
- **Integridad de Memoria y Poda por Turnos (DATA-01):** Poda FIFO que preserva el prompt del sistema y mantiene indivisibles los pares de llamadas y resultados de herramientas.
- **Concurrencia SQLite y Modo WAL:** `PRAGMA busy_timeout = 10000` y `PRAGMA journal_mode = WAL` para concurrencia multi-lector sin contención. Bases existentes transicionan automáticamente sin recreación de tablas.
- **Paridad Bilingüe en Documentación:** Paridad 100% en inglés y español en README y CHANGELOG.

### Guía de Migración
Si ya instalaste o integraste la versión v0.2.0:
1. **Configurá `WHATSAPP_APP_SECRET`:** Agregá tu App Secret de Meta a las variables de entorno y pasalo a `WhatsAppChannel(..., app_secret=os.environ["WHATSAPP_APP_SECRET"])`. Si estás testeando localmente sin firma, pasá explícitamente `verify_signature=False`.
2. **Actualizá el parseo de respuesta del Webhook:** Si tenías clientes o scripts esperando el campo sincrónico `reply` en el JSON de respuesta de POST `/webhook`, actualizalos para esperar `{"status": "success", "messages_queued": N}`.
3. **Reducí el valor de `max_turns`:** Si tu configuración anterior inflaba `max_turns` para contar mensajes sueltos (por ejemplo, `max_turns=40` para retener unos ~10 turnos reales), reducilo al número real de turnos deseados (por ejemplo, bajalo a `max_turns=10`). Mantener el número anterior retendrá aproximadamente 4 veces más contexto que antes.
